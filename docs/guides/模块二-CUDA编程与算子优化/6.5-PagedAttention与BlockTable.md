## 1. PagedAttention 解决哪个问题

PagedAttention 的主要目标是让推理服务更高效地存放和复用 KV Cache。它不是一种新的 Softmax 公式，也不等于 Flash-Decoding。

| 技术 | 核心问题 | 主要动作 |
| --- | --- | --- |
| FlashAttention | Prefill/训练中间矩阵的 HBM IO | 分块、片上计算、重计算 |
| Flash-Decoding | 单 token Decode 的执行并行度 | 沿 KV 长度做 Split-KV |
| PagedAttention | 动态请求的 KV Cache 分配与寻址 | 固定 block、页表映射、共享/回收 |

实际引擎可以同时使用分页 KV Cache 和 Split-KV kernel。前者决定 K/V 在哪里，后者决定如何并行扫描它们。

## 2. 连续 KV Cache 为什么浪费

在线服务无法提前知道每个请求最终会生成多少 token。如果按最大长度给每个请求预留连续空间，短请求会留下大量未使用容量；如果只按当前长度分配，序列增长时又可能需要搬迁或寻找更大的连续区域。

请求长度和到达/结束时间还不同，释放后的空洞未必正好适合下一个请求。需要区分两类浪费：

- **内部碎片**：已经分给某请求、但请求没有使用的空间；
- **外部碎片**：总空闲量足够，但被切成无法满足连续分配的小块。

分页打破“一个序列必须物理连续”的约束。请求只需在逻辑上连续，物理 block 可以来自全局池的任意位置。

## 3. 逻辑块、物理块与 Block Table

![PagedAttention 的逻辑 token、Block Table 与物理 KV Cache 映射](/AIInfraGuide/images/cuda-optimization/paged-attention-block-table.svg)

*图：本站据 vLLM 官方 PagedAttention 教程重绘。相邻逻辑块可以映射到不相邻物理块；最后一个 block 未填满的部分是主要内部碎片。*

假设 `block_size = 4`，一个长度为 10 的序列需要 3 个逻辑 block：

```text
logical block 0: token 0..3
logical block 1: token 4..7
logical block 2: token 8..9 + 两个未用槽位
```

若它的 `block_table = [7, 2, 5]`，则三个逻辑块分别存放在物理 block 7、2、5。追加 token 10 和 11 时仍写入物理 block 5；追加 token 12 时再申请一个新物理 block。

对长度为 `L` 的序列，需要的 block 数为：

$$
N_{blocks}=\left\lceil\frac{L}{block\_size}\right\rceil
$$

最后一个 block 的未使用槽位不超过 `block_size - 1`。因此 block 越小，最坏内部碎片越少；但页表更长、调度元数据更多，kernel 的访问粒度也更碎。

## 4. 从 token 位置计算物理地址

逻辑 token `t` 先分解为逻辑块号和块内偏移：

$$
logical\_block=\left\lfloor\frac{t}{block\_size}\right\rfloor
$$

$$
offset=t\bmod block\_size
$$

再查页表得到物理块：

$$
physical\_block=block\_table[logical\_block]
$$

简化的 CUDA 风格寻址如下。实际 vLLM 布局会为了向量化、head 分组和缓存友好做更多维度重排，不能把这个线性布局当成源码的逐字翻译。

```cuda
__device__ float load_k(
    const half* k_cache,
    const int* block_table,
    int logical_token,
    int kv_head,
    int dim,
    int block_size,
    int num_kv_heads,
    int head_dim) {

    int logical_block = logical_token / block_size;
    int offset = logical_token % block_size;
    int physical_block = block_table[logical_block];

    size_t index = (((size_t)physical_block * block_size + offset)
                    * num_kv_heads + kv_head) * head_dim + dim;
    return __half2float(k_cache[index]);
}
```

这个多一次的表查找不是免费的，但它换来了按需分配、快速回收和跨请求共享。是否值得，必须在完整服务负载下用显存容量和吞吐一起评估。

## 5. Kernel 读取时还要处理什么

### 5.1 最后一个 block 的有效长度

物理 block 存在不代表所有槽位都有效。kernel 仍需检查 `logical_token < seq_len`，避免把未初始化槽位参与点积和 Softmax。

### 5.2 GQA/MQA 的 Head 映射

在 GQA/MQA 中，Query Head 数大于 KV Head 数。常见映射可以写成：

```cpp
int queries_per_kv = num_query_heads / num_kv_heads;
int kv_head = query_head / queries_per_kv;
```

直接拿 `query_head` 索引 KV Cache 可能越界，也可能读到合法但错误的 head，后者更难发现。

### 5.3 向量化与对齐

为了合并访存，实际 kernel 常让线程组一起加载一个 token 的连续 `head_dim` 元素，并使用 `half2`、`float4` 或更宽的向量类型。布局、block size、head dimension 和线程组大小因此需要协同设计。

### 5.4 不连续物理块

同一物理 block 内仍是连续的；跳到下一个逻辑 block 时才重新查表。合理的 block size 能在分页灵活性和局部连续访问之间取得平衡。

## 6. Prefix 共享与 Copy-on-Write

多个请求拥有相同前缀时，可以让它们的 Block Table 指向同一组只读物理 block，并维护引用计数。这样不必复制相同的 prefix KV。

当某个请求要修改共享 block 时，需要 Copy-on-Write：

1. 发现目标物理 block 的引用计数大于 1；
2. 申请新 block 并复制有效数据；
3. 只更新当前请求的 Block Table；
4. 递减旧 block 的引用计数。

这里的“共享”是存储层能力。Prefix Cache 还需要决定哪些前缀可命中、何时驱逐，以及如何处理模型、LoRA、位置编码等缓存键；这些系统问题放在模块四的 Prefix Cache 小节。

## 7. 最小地址验证实验

先用极小整数张量验证逻辑到物理映射，再接入 Attention：

```python
import torch

block_size = 4
num_physical_blocks = 4
head_dim = 2

# 每个物理 block 填入可识别的值，便于检查读到了哪里。
pool = torch.arange(
    num_physical_blocks * block_size * head_dim
).reshape(num_physical_blocks, block_size, head_dim)

block_table = torch.tensor([2, 0, 3])
seq_len = 10

def paged_gather(pool, table, length):
    rows = []
    for token in range(length):
        logical_block, offset = divmod(token, block_size)
        physical_block = table[logical_block]
        rows.append(pool[physical_block, offset])
    return torch.stack(rows)

actual = paged_gather(pool, block_table, seq_len)
expected = torch.cat([pool[2], pool[0], pool[3, :2]], dim=0)
torch.testing.assert_close(actual, expected)
```

迁移到 GPU kernel 后，至少覆盖：空序列之外的最短长度、恰好填满 block、跨 block、最后一块未填满、乱序物理映射、重复共享 block 和 GQA head 映射。

## 8. 怎样评估分页方案

只测单 kernel 延迟不能回答分页是否有效。建议同时记录：

| 层次 | 指标 |
| --- | --- |
| 地址正确性 | 每个逻辑 token 实际读取的物理 block/offset |
| Kernel | Decode Attention 延迟、DRAM throughput、warp stall |
| KV 管理器 | 已用 block、空闲 block、内部碎片、分配/回收次数 |
| 服务 | TTFT、TPOT、P50/P95、吞吐、最大并发请求数 |

对比时固定模型、dtype、KV block size、prompt/output 长度分布、并发和调度策略。PagedAttention 的主要价值常在混合长度和动态请求下体现；单个固定长度请求不足以代表生产负载。

## 9. 常见错误

### 9.1 把逻辑 block 号当物理 block 号

所有跨 block 的读取都必须经过 Block Table。只在第一个 block 查表、后面假设物理连续，会在某些分配顺序下静默读错。

### 9.2 只按物理容量做边界判断

最后一个 block 的未用槽位属于已分配显存，但不属于当前序列。必须用真实 `seq_len` mask。

### 9.3 只宣传“消除碎片”

分页仍有最后一块的内部碎片、页表元数据和间接寻址成本。更准确的说法是把浪费限制在 block 粒度，并改善动态分配与共享能力。

### 9.4 用本站简化布局替代 vLLM 当前实现

vLLM 内核会演进，后端也不止一个。本页伪代码用于建立地址模型，线程/向量布局应回到当前版本的设计文档和源码核对。

## 总结

- PagedAttention 把逻辑连续的 KV 序列映射到固定大小、可离散分配的物理 block。
- Block Table 是逻辑 token 到物理地址的关键；kernel 还必须处理尾块、GQA 和向量化布局。
- 分页为按需分配、快速回收、Prefix 共享和 Copy-on-Write 提供基础，但也引入元数据和间接寻址成本。
- 正确评估要同时看 kernel、KV 管理器和完整服务指标。
