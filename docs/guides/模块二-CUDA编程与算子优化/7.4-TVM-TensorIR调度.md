## 1. TensorIR 要分开哪两件事

张量算子的数学定义与硬件执行方式是两类决策。

以矩阵乘为例，计算定义是：

$$
C_{i,j}=\sum_k A_{i,k}B_{k,j}
$$

调度则回答：

- `i/j/k` 分别切多大 tile；
- 哪些循环绑定 CUDA block/thread；
- A/B 是否缓存到 shared memory；
- 哪些局部结果留在寄存器；
- 是否向量化、展开或软件流水；
- 如何处理不能整除 tile 的尾部。

TensorIR 让计算和调度在 IR 中都有显式表示。你可以保留同一数学定义，为不同硬件或 shape 生成不同 schedule。

## 2. 先读懂 PrimFunc 与 Block

下面是简化的逐元素加法 TensorIR：

```python
from tvm.script import tir as T

@T.prim_func
def add(
    A: T.Buffer((128,), "float32"),
    B: T.Buffer((128,), "float32"),
    C: T.Buffer((128,), "float32"),
):
    for i in range(128):
        with T.block("C"):
            vi = T.axis.spatial(128, i)
            C[vi] = A[vi] + B[vi]
```

阅读时按以下顺序：

1. **PrimFunc 参数**：输入输出 Buffer 的 shape、dtype；
2. **循环**：当前程序怎样遍历索引空间；
3. **Block**：调度和依赖分析使用的计算区域；
4. **Block axis**：spatial、reduce 或其他迭代类型；
5. **读写集合**：哪些 Buffer 区域被读取和写入。

Block 不是 CUDA thread block。它首先是 TensorIR 中的计算抽象；只有经过 thread binding 后，某些循环才会映射到 GPU 的 `blockIdx` 或 `threadIdx`。

## 3. Schedule 变换到底改了什么

![TensorIR 从朴素循环到 GPU 调度的变换](/AIInfraGuide/images/cuda-optimization/tensorir-schedule-transform.svg)

*图：本站据 TVM TensorIR Creation/Transformation 教程重绘。每一步都生成新的 IR；箭头不是性能保证，tile 和绑定参数仍需测量。*

对一个长度为 `N` 的循环，可以从最小调度开始：

```python
sch = tvm.tir.Schedule(add)
block = sch.get_block("C")
i, = sch.get_loops(block)
io, ii = sch.split(i, factors=[None, 128])
sch.bind(io, "blockIdx.x")
sch.bind(ii, "threadIdx.x")
```

变换后的索引近似为：

```text
for blockIdx.x in ceildiv(N, 128):
    for threadIdx.x in 128:
        i = blockIdx.x * 128 + threadIdx.x
        if i < N:
            C[i] = A[i] + B[i]
```

核心 primitive 的作用要结合变换前后 IR 理解：

| Primitive | 主要变化 | 需要检查 |
| --- | --- | --- |
| `split` | 一个循环变成多级循环 | 因子、尾部 predicate |
| `reorder` | 改变循环嵌套顺序 | 数据依赖是否合法 |
| `fuse` | 多个循环合成一个索引空间 | 反解索引与并行粒度 |
| `bind` | 循环绑定线程轴 | grid 范围与硬件限制 |
| `cache_read/write` | 引入局部缓存 stage | memory scope、同步、容量 |
| `compute_at` | 改变生产者计算位置 | 重计算与复用的取舍 |
| `vectorize` | 显式向量化某级循环 | 对齐、尾部和目标支持 |

每执行一个 primitive 就打印 IR，比一次写完一长串调度更容易定位依赖错误和性能退化。

## 4. GPU 调度的基本路径

一个真实 GPU 算子通常逐步完成：

1. **空间轴 tile**：生成 grid 与 block 内的工作；
2. **归约轴 tile**：决定每次载入和累加的 K 范围；
3. **缓存**：把可复用数据放到 shared/local；
4. **合作加载**：让线程共同加载连续数据；
5. **同步**：在生产者/消费者之间保证可见性；
6. **向量化或 Tensor Core 映射**：匹配目标硬件；
7. **尾部处理**：保证任意 shape 正确。

以 Matmul 为例，只做 `bind` 往往仍会重复从 global memory 读取 A/B；只做 shared cache 又可能因 tile 过大降低 occupancy。调度是多个资源约束的组合，不是 primitive 清单越长越快。

## 5. 从 IR 到可执行模块

调度完成后，要指定 target 并构建：

```python
import tvm

mod = tvm.build(sch.mod, target="cuda")
print(mod.imported_modules[0].get_source())
```

这里至少检查三层结果：

1. **Scheduled TensorIR**：循环、Buffer scope 和线程绑定是否符合预期；
2. **生成的 CUDA/PTX**：向量化、同步、load/store 是否实际出现；
3. **运行时 trace/profile**：kernel 数、时间和带宽是否改善。

只看 Python schedule 不能确认编译器最终生成了什么；只看单个 kernel 又可能忽略 runtime、布局转换和多个算子之间的成本。

## 6. 正确性与性能实验

### 6.1 正确性先行

使用 NumPy 或 PyTorch 参考实现，覆盖正常和边界 shape：

```python
import numpy as np
import tvm

n = 128
a_np = np.random.randn(n).astype("float32")
b_np = np.random.randn(n).astype("float32")

a = tvm.nd.array(a_np, device=tvm.cuda())
b = tvm.nd.array(b_np, device=tvm.cuda())
c = tvm.nd.empty((n,), "float32", device=tvm.cuda())

mod(a, b, c)
np.testing.assert_allclose(c.numpy(), a_np + b_np, rtol=1e-5, atol=1e-5)
```

上面先验证与示例 PrimFunc 一致的固定长度。接着把 PrimFunc 的 Buffer shape 和输入一起改成 127、129、1000，并为每个 shape 重新创建 schedule、构建 `mod`；这样才能确认 `split(..., factors=[None, 128])` 生成的 predicate 和 Buffer 边界正确。若项目使用符号 shape，则还要单独检查动态版本的函数签名和运行时参数，不能把固定 128 的模块直接喂给长度 1000 的 Buffer。

### 6.2 分开编译时间与稳态时间

构建、首次加载和首次运行不应混进 kernel 稳态延迟。使用 TVM 的 time evaluator 或目标设备同步机制，记录 warmup、重复次数和统计方式。

建议保留一张实验表：

| 版本 | Shape | Schedule 摘要 | 编译时间 | 稳态延迟 | 最大误差 |
| --- | --- | --- | ---: | ---: | ---: |
| baseline | ... | serial loops | ... | ... | ... |
| GPU v1 | ... | split + bind | ... | ... | ... |
| GPU v2 | ... | + shared cache | ... | ... | ... |

没有正确性列的性能表是不完整的；没有编译时间列也无法判断动态 shape 场景是否值得。

## 7. TensorIR、Relax 与自动调优

TensorIR 主要表达底层张量程序和调度。TVM 的更高层模型表示、图变换和部署流程还会涉及 Relax；不同 TVM 版本的推荐入口会变化，应以对应版本官方文档为准。

当调度参数空间变大时，可以使用 MetaSchedule 等测量驱动方法搜索候选。但自动调优不是跳过理解：

- 搜索空间仍由人定义；
- 测量需要稳定且与部署硬件一致；
- 动态 shape 需要 workload 分桶或可泛化 schedule；
- 最佳单算子配置未必带来最佳端到端结果。

## 8. 什么时候选择 TVM

TVM 更有价值的场景包括：

- 同一模型或算子要覆盖 CUDA、CPU 和其他后端；
- 需要显式控制算子 schedule，又希望保留统一 IR；
- 部署形状相对明确，可以接受编译和调优成本；
- 需要生成独立 artifact 并接入 TVM runtime；
- 团队愿意维护 target、schedule 和测量数据库。

若只在 PyTorch/NVIDIA 中快速写一个自定义 Softmax，Triton 通常学习路径更短。若问题是 PyTorch 图捕获和自动融合，先使用 `torch.compile`。工具选择从工程边界出发，不从“谁更高级”出发。

## 9. 常见错误

### 9.1 把 TensorIR Block 当 CUDA Block

前者是调度与依赖分析的计算区域，后者是 GPU 执行层级。只有 `bind` 后的循环轴才明确映射到 CUDA 线程层次。

### 9.2 只看变换脚本，不看变换后 IR

Schedule primitive 作用于当前 IR 中的具体循环和 block。前序变换改变结构后，后续 primitive 的目标也可能变化；每一步都应检查输出。

### 9.3 用教程固定 shape 推广到动态 shape

能整除 tile 的形状可能没有 predicate，换一个长度就越界或触发另一套代码。至少加入非整除和极小 shape。

### 9.4 把自动调优结果当成永久最优

结果依赖硬件、驱动、编译器版本、shape 和测量噪声。升级环境后要重跑代表性 workload。

## 总结

- TensorIR 把张量计算与硬件调度显式分开，让同一语义可以有多个目标实现。
- 学习主线应是 Creation → Transformation → Build → Correctness → Benchmark。
- Schedule primitive 必须通过变换后 IR、生成代码和 profiler 三层验证。
- TVM 的优势主要在可编程调度、跨硬件编译和部署栈；代价是更高的编译与维护复杂度。
