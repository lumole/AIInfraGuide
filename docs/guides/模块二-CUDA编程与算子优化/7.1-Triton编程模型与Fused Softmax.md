Triton 不是“把 CUDA 关键字改成 Python”，它提供了另一种 Kernel 编程抽象：程序员描述一个 program instance 处理的 Block，编译器再把 Block 映射到线程、Warp、寄存器和共享内存。

本文使用两个由浅入深的例子：向量加法和按行 Softmax。目标不是隐藏 GPU 原理，而是理解哪些细节仍然由你负责，哪些细节交给 Triton 编译器完成。

## 1. CUDA Thread 与 Triton Program 的对应关系

CUDA 常从一个线程出发：每个线程计算一个或几个元素，然后用 Warp、共享内存和同步完成协作。Triton 则从一个 Block 出发：每个 program instance 取得一个 `pid`，生成一组 offsets，一次加载一个向量或矩阵 tile。

| CUDA | Triton | 说明 |
| --- | --- | --- |
| `blockIdx.x` | `tl.program_id(0)` | 当前 program 在 grid 中的编号 |
| `threadIdx.x` | `tl.arange(0, BLOCK_SIZE)` | 一个 Block 内的逻辑元素索引 |
| `if (i < n)` | `mask=i < n` | 对越界元素做 predication |
| `__syncthreads()` | 通常由编译器安排 | 不能在 Triton 中任意插入线程级同步 |
| shared memory / register tiling | `tl.load`、`tl.store`、`tl.dot` 的 tile | 由编译器结合配置生成 |

```mermaid
flowchart LR
    A[Python 函数] --> B[@triton.jit Kernel]
    B --> C[tl.program_id / arange / load / store]
    C --> D[编译器选择线程与内存布局]
    D --> E[PTX/SASS Kernel]
    E --> F[GPU 执行多个 program instance]
```

Triton 仍然要求你理解合并访存、tile 大小、寄存器压力和数值精度。抽象层次更高，不代表性能问题消失。

## 2. 安装与第一个向量加法 Kernel

在 Linux + NVIDIA GPU 上，建议先准备独立 Python 环境：

```bash
python -m venv .venv-triton
source .venv-triton/bin/activate
pip install --upgrade pip
pip install torch triton
```

Triton 版本需要和 PyTorch、CUDA 驱动匹配。先运行官方向量加法教程中的最小例子，再开始修改 Kernel。

```python
import torch
import triton
import triton.language as tl

@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n_elements,
               BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(axis=0)
    offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements

    x = tl.load(x_ptr + offsets, mask=mask, other=0.0)
    y = tl.load(y_ptr + offsets, mask=mask, other=0.0)
    tl.store(out_ptr + offsets, x + y, mask=mask)

def add(x: torch.Tensor, y: torch.Tensor):
    assert x.is_cuda and y.is_cuda
    assert x.shape == y.shape
    out = torch.empty_like(x)
    n = out.numel()
    grid = lambda meta: (triton.cdiv(n, meta["BLOCK_SIZE"]),)
    add_kernel[grid](x, y, out, n, BLOCK_SIZE=1024)
    return out
```

调用方只决定 grid 和 meta 参数；每个 program instance 负责 `[pid * BLOCK_SIZE, (pid+1) * BLOCK_SIZE)`。

## 3. Mask 是 Triton 正确性的核心

`tl.arange` 通常会生成一个 2 的幂大小的向量，因此最后一个 program 很可能包含超出真实长度的 lanes。所有可能越界的加载和存储都要带 mask：

```python
mask = offsets < n_elements
x = tl.load(x_ptr + offsets, mask=mask, other=0.0)
tl.store(out_ptr + offsets, x, mask=mask)
```

规约类算子还要正确设置 `other`：

- 求最大值时，越界元素应为 `-inf`；
- 求和时，越界元素应为 `0`；
- Softmax 写回时，越界位置不能写入输出。

一个常见错误是加载时使用 `other=0.0`，然后直接做 `tl.max`。当真实数据全是负数时，越界的 0 会错误地成为最大值，最终结果看起来只是“有一点偏差”，但根因是 Mask 错了。

## 4. Fused Softmax 完整实现

下面的 Kernel 每个 program 处理一行。它把加载、减最大值、指数、求和和写出放在同一个 Kernel 中，和第 5 章的 CUDA 实现一一对应：

```python
@triton.jit
def softmax_kernel(output_ptr, input_ptr,
                   input_row_stride, output_row_stride,
                   n_cols,
                   BLOCK_SIZE: tl.constexpr):
    row = tl.program_id(0)
    row_start = input_ptr + row * input_row_stride
    col_offsets = tl.arange(0, BLOCK_SIZE)
    mask = col_offsets < n_cols

    x = tl.load(row_start + col_offsets, mask=mask, other=-float("inf"))
    x = x.to(tl.float32)

    row_max = tl.max(x, axis=0)
    numerator = tl.exp(x - row_max)
    denominator = tl.sum(numerator, axis=0)
    y = numerator / denominator

    out_start = output_ptr + row * output_row_stride
    tl.store(out_start + col_offsets, y, mask=mask)

def triton_softmax(x: torch.Tensor):
    assert x.is_cuda and x.ndim == 2
    n_rows, n_cols = x.shape
    y = torch.empty_like(x)
    block_size = triton.next_power_of_2(n_cols)
    softmax_kernel[(n_rows,)](
        y, x,
        x.stride(0), y.stride(0), n_cols,
        BLOCK_SIZE=block_size,
    )
    return y
```

这里把输入转换到 FP32 再做规约，是为了避免低精度 `max/sum` 的误差。输出仍然可以保持输入 dtype。

### 4.1 处理超大列数

如果 `n_cols` 很大，`BLOCK_SIZE` 也会很大，单个 program 的寄存器和临时存储可能超过限制。此时不能简单地继续增大 `BLOCK_SIZE`，而应该：

- 将一行分成多个 tile，分两阶段规约；
- 改用 Online Softmax；
- 或直接使用 PyTorch/FlashAttention/cuDNN 已经优化过的实现。

## 5. 调优 BLOCK_SIZE 与 num_warps

正确实现只是起点。Triton 的 tile 形状决定了：

- 一个 program 处理多少元素；
- 使用多少 Warp；
- 每线程寄存器数量；
- Occupancy 和内存合并方式。

可以给 Kernel 增加 `num_warps`：

```python
softmax_kernel[(n_rows,)](
    y, x,
    x.stride(0), y.stride(0), n_cols,
    BLOCK_SIZE=block_size,
    num_warps=4,
)
```

一个实用的搜索起点：

| 列数 | BLOCK_SIZE 候选 | num_warps 候选 |
| --- | --- | --- |
| `<=128` | 128 | 2, 4 |
| `129~512` | 256, 512 | 4, 8 |
| `513~2048` | 1024, 2048 | 4, 8 |
| 更大 | 分块/Online Softmax | 视实现而定 |

不要根据这张表直接选生产参数。使用自己的 shape 做自动调优，并记录编译时间和运行时间；首次调用包含编译成本，不能和稳定运行时间混在一起。

## 6. 正确性与性能测试

### 6.1 结果校验

```python
torch.manual_seed(0)
for shape in [(3, 127), (32, 512), (4096, 4096)]:
    x = torch.randn(shape, device="cuda", dtype=torch.float16)
    actual = triton_softmax(x)
    expected = torch.softmax(x, dim=-1)
    torch.testing.assert_close(actual, expected, rtol=1e-3, atol=1e-3)
```

测试以下边界：

- 列数不是 2 的幂；
- 输入包含很大的正负值；
- 行数为 1；
- 非 contiguous 的输入（如果 Kernel 支持 stride）；
- FP16、BF16 和 FP32。

### 6.2 基准测试

```python
from triton.testing import do_bench

x = torch.randn((4096, 4096), device="cuda", dtype=torch.float16)
print("triton ms:", do_bench(lambda: triton_softmax(x)))
print("torch ms:", do_bench(lambda: torch.softmax(x, dim=-1)))
```

只比较 Kernel 时间还不够。还应比较端到端模型延迟，并确认 Triton 编译缓存已经命中。若在真实模型中 Softmax 前后还有其他逐元素操作，可以把它们放入同一个 Triton Kernel，再与单独 Softmax 比较。

## 7. 什么时候应该回到 CUDA

Triton 适合：

- 规则的 tile 计算、逐元素操作、归约和常见 GEMM；
- 需要快速迭代的模型自定义算子；
- 想让同一份 Python Kernel 覆盖多个相近 shape；
- 需要和 PyTorch 自动微分或 `torch.compile` 组合。

手写 CUDA/CUTLASS 更适合：

- 需要精确控制 shared-memory swizzle、异步拷贝或特殊指令；
- 使用 Hopper TMA/WGMMA 等 Triton 尚未完整暴露的能力；
- 算子包含复杂线程协作、跨 Block 通信或特殊硬件路径；
- 已经用 profiler 证明该热点值得长期维护。

选择标准不是“谁更底层”，而是开发成本、性能上限、形状稳定性和维护团队的综合结果。

## 8. 动手实验

1. 用向量加法验证 `pid -> offsets -> mask` 映射。
2. 把 `other=0.0` 错误地用于 Softmax max 规约，构造负值输入观察结果如何出错。
3. 实现 `scale + mask + softmax` 的 fused Kernel，比较第 5.3 节 CUDA 版本。
4. 对 `BLOCK_SIZE` 和 `num_warps` 做网格搜索，画出 shape 到延迟的表格。
5. 用 `TRITON_PRINT_AUTOTUNING=1` 或编译日志观察调优配置，记录首次编译成本。
6. 对 Triton Kernel 使用 Nsight Compute，确认它的内存吞吐和寄存器用量。

## 总结

- Triton 的核心抽象是 Block-level program，不是把每个 CUDA thread 显式写出来。
- `mask` 决定边界正确性；规约时必须给越界元素正确的 identity value。
- Fused Softmax 的关键是 FP32 统计量、合适的 `BLOCK_SIZE` 和避免超大单行 tile。
- 性能调优要同时看编译成本、Kernel 延迟和端到端收益。
- Triton 和 CUDA 是互补关系：先用更高层抽象快速验证，再在 profiler 证据充分时下沉到 CUDA。
