## 1. 先区分 Prefill 与 Decode

标准 Attention 都可以写成：

$$
O = \operatorname{softmax}\left(\frac{QK^T}{\sqrt d}\right)V
$$

但 Prefill 和 Decode 的形状不同，适合的并行方法也不同。

| 阶段 | `Q` 的序列长度 | `K/V` 的序列长度 | 主要并行来源 |
| --- | ---: | ---: | --- |
| Prefill / 训练 | 通常较长 | 与输入长度接近 | Batch、Head、Q tile、KV tile |
| Decode | 通常为 1 | 随已生成 token 增长 | Batch、Head、KV 分片 |

FlashAttention V1/V2 的核心是让长 `Q` 和 `K/V` 按 tile 流过片上存储。Decode 时每个请求每一步通常只有一个新 Query；若仍让一个 CUDA block 负责一个 Query Head，就可能没有足够多的 block 填满 GPU。

Flash-Decoding 解决的是这个执行并行度问题。它不负责 KV Cache 的分配、回收或跨请求共享；这些属于下一节 PagedAttention 的范围。

## 2. 并行度为什么会不足

设一次 Decode 的张量近似为：

```text
Q: [batch, query_heads, 1, head_dim]
K: [batch, kv_heads, kv_length, head_dim]
V: [batch, kv_heads, kv_length, head_dim]
```

如果一个 block 处理一个 `(request, query_head)`，可启动的 block 数量大约是 `batch × query_heads`。当 batch 很小而 KV 很长时，每个 block 要顺序扫描大量 K/V，其他 SM 却可能空闲。

仅增加 block 内线程数不能无限扩展：线程仍在同一个 block 中共享资源，block 数量没有增加。Flash-Decoding 因此再引入一个 `split` 维度：

$$
\text{grid} \approx \text{batch} \times \text{query heads} \times \text{KV splits}
$$

这会增加中间结果和一次归约，但能让长上下文的小批量 Decode 暴露更多独立工作。

## 3. Split-KV 的三步计算

![Flash-Decoding 沿 KV 序列切分并归约局部状态](/AIInfraGuide/images/cuda-optimization/flash-decoding-split-reduction.svg)

*图：本站据 PyTorch/Stanford Flash-Decoding 教程重绘。左侧多个分片可以并行，右侧只归约很小的统计量，而不是物化完整注意力矩阵。*

设 KV 长度为 `L`，切成 `P` 个区间。第 `p` 个 block 只扫描自己的 `K_p/V_p`。

### 3.1 每个分片计算局部状态

对局部分数 $s_p=qK_p^T/\sqrt d$，保存三个量：

$$
m_p = \max(s_p)
$$

$$
l_p = \sum_j e^{s_{p,j}-m_p}
$$

$$
o_p = \sum_j e^{s_{p,j}-m_p}V_{p,j}
$$

`o_p` 是尚未除以 `l_p` 的向量。这样，每个分片只写出两个标量和一个 `head_dim` 向量，不需要把完整 score 行写回 HBM。

### 3.2 保存局部结果

中间缓冲区规模约为：

$$
P \times (2 + d) \times \text{sizeof(accumulator)}
$$

它随分片数和 head dimension 增长，而不随完整 KV 长度线性增长。实现中常让 `m/l` 使用 FP32；低精度输入不意味着归约状态也应使用低精度。

### 3.3 第二阶段归约

归约 kernel 读取 `P` 组 `(m_p,l_p,o_p)`，合并为全局 `(m,l,o)`，最后输出 `o/l`。一些实现会融合或分层完成这一步，但数学规则相同。

## 4. 局部状态怎样稳定合并

合并分片 `a` 与 `b` 时，先取共同最大值：

$$
m=\max(m_a,m_b)
$$

再把两个分片都缩放到相同指数基准：

$$
l=l_a e^{m_a-m}+l_b e^{m_b-m}
$$

$$
o=o_a e^{m_a-m}+o_b e^{m_b-m}
$$

最终归一化输出为 `o/l`。这正是 5.2 Online Softmax 合并公式在 Attention 上的应用。

不能直接平均 `o_a/l_a` 与 `o_b/l_b`。两个分片的分数分布、长度和最大值都可能不同，局部归一化后的向量没有相同权重。

```python
import torch

def merge_state(a, b):
    ma, la, oa = a
    mb, lb, ob = b
    m = torch.maximum(ma, mb)
    wa = torch.exp(ma - m)
    wb = torch.exp(mb - m)
    return m, wa * la + wb * lb, wa * oa + wb * ob
```

由于这个合并操作满足结合性，可以顺序归约，也可以用树形归约降低归约深度。

## 5. 最小正确性实验

先不要写 CUDA。用下面的 PyTorch 版本确认你理解的状态定义与合并顺序是对的：

```python
import math
import torch

def local_state(q, k, v):
    scores = (q.float() @ k.float().T) / math.sqrt(q.numel())
    m = scores.max()
    weights = torch.exp(scores - m)
    l = weights.sum()
    o = weights @ v.float()
    return m, l, o

@torch.no_grad()
def split_kv_attention(q, k, v, splits):
    states = [
        local_state(q, kc, vc)
        for kc, vc in zip(k.chunk(splits), v.chunk(splits))
    ]
    while len(states) > 1:
        merged = []
        for i in range(0, len(states), 2):
            merged.append(
                merge_state(states[i], states[i + 1])
                if i + 1 < len(states) else states[i]
            )
        states = merged
    _, l, o = states[0]
    return o / l

device = "cuda"
q = torch.randn(128, device=device, dtype=torch.float16)
k = torch.randn(8192, 128, device=device, dtype=torch.float16)
v = torch.randn(8192, 128, device=device, dtype=torch.float16)

expected = torch.softmax(
    (q.float() @ k.float().T) / math.sqrt(128), dim=-1
) @ v.float()

for splits in (1, 2, 4, 8, 16):
    actual = split_kv_attention(q, k, v, splits)
    torch.testing.assert_close(actual, expected, rtol=1e-5, atol=1e-5)
```

这个程序验证数学，不代表高性能实现：Python 循环、`chunk` 和逐分片 kernel launch 会把调度开销放大。下一步才是把局部扫描写成一个 CUDA/Triton kernel，把归约写成另一个 kernel。

## 6. 分片数不是越多越好

增加 `P` 同时带来收益和成本：

| 增加分片后的变化 | 影响 |
| --- | --- |
| 可并行 block 数增加 | 小 batch、长 KV 时更容易填满 GPU |
| 每片扫描长度缩短 | 单 block 工作时间下降 |
| 中间 `(m,l,o)` 增加 | HBM 写入和归约成本上升 |
| block 更碎 | launch、尾块和调度开销占比上升 |

因此分片策略至少要观察 batch、query heads、KV 长度、head dimension、GPU SM 数和当前是否还有其他请求。短上下文或大 batch 下，原有并行度可能已经足够，Split-KV 反而更慢。

## 7. 怎样做可信的性能实验

建议把实验拆成三组，不把数学验证和性能结论混在一起：

1. **正确性**：随机值、极端值、非整除长度；对比 FP32 参考实现与不同 split 数。
2. **Kernel 时间**：预热后用 CUDA Event 记录局部扫描、归约和端到端时间，显式同步。
3. **系统效果**：固定模型、并发、prompt 长度和生成长度，记录 TPOT、P50/P95 和 KV Cache 占用。

在 `sshdh` 上做实验时，应记录 RTX 3060、CUDA/PyTorch 版本和 shape。它可以验证公式和普通 CUDA 路径，但不能用来宣称 H100 或生产 vLLM 的吞吐。

## 8. 常见错误

### 8.1 把 Flash-Decoding 当成 FlashAttention V2 的固定配置

两者共享 Online Softmax 数学，但网格维度不同。Prefill 有长 Q 维度；Decode 需要从 KV 分片补并行度，不能直接套同一组 tile 和 launch 参数。

### 8.2 合并已经归一化的局部输出

必须保留未归一化 `o_p`、局部分母 `l_p` 和最大值 `m_p`。只保存 `o_p/l_p` 会丢失正确合并所需的信息。

### 8.3 只测局部扫描 kernel

Split-KV 的代价包括中间写入和最终归约。只报告第一阶段时间会系统性高估收益。

### 8.4 对所有长度固定使用同一分片数

最佳分片数与 shape 和并发相关。生产实现通常需要启发式规则或测量驱动的选择，而不是硬编码 `P=8`。

## 总结

- Decode 的 Query 通常只有一个 token，长 KV、小 batch 时可能缺少可并行的 CUDA block。
- Flash-Decoding 沿 KV 序列切分，每片生成 `(m,l,o)`，再用稳定的 Online Softmax 规则归约。
- 分片增加并行度，也增加中间结果、归约和调度开销；是否使用要由实测决定。
- 它优化的是 Attention 执行，PagedAttention 管理的是 KV Cache 存储，两者可以组合但不是同一种技术。
