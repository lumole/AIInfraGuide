## 主教程

本节的主线是 MLIR 官方 [Toy Tutorial](https://mlir.llvm.org/docs/Tutorials/Toy/)。它不是 API 索引，而是从一个小语言开始，依次构造 AST、定义 Toy Dialect、加入形状推断与优化、Lower 到 Affine/LLVM，最后生成可执行代码。第一次学习时建议按 Chapter 1 → 2 → 3 → 5 → 6 的顺序走通，再回头看泛型调用和接口细节。

配套阅读 [MLIR Language Reference](https://mlir.llvm.org/docs/LangRef/) 时只查当前遇到的语法，不要从头背规范。本站负责把 Toy 教程中的对象放进 AI 编译器坐标系，并用同一个矩阵计算展示“语义逐层减少、硬件细节逐层增加”。

> **阅读目标**：能区分 Operation、Dialect、Pass、Rewrite 和 Conversion，并能从一段高层 IR 追到低层 IR，而不是只记住 MLIR 是“某种中间表示”。

## 1. MLIR 解决什么问题

传统编译器常从源语言 IR 快速降到 LLVM IR。对机器学习和异构硬件而言，过早变低级会丢失张量形状、布局、并行维度和算子语义；这些恰好是融合、分块和设备映射所需的信息。

MLIR 提供的是构建多层编译器的基础设施：

- 用 **Dialect** 表达某一领域的操作、类型与属性；
- 让不同抽象层的 IR 可以在同一个框架内共存；
- 用 Pass 和 Rewrite 在某一层做优化；
- 用 Conversion 把一组操作逐步变成更低层、在目标环境中合法的操作。

它不是一个固定的“自动让模型更快”的产品。真正的优化策略来自使用 MLIR 的编译器项目及其 Dialect、Pass、成本模型和后端。

## 2. 一段程序为什么需要多层 IR

![从模型语义到目标代码的多层 IR Lowering](/AIInfraGuide/images/cuda-optimization/compiler-ir-lowering.svg)

*图：本站据 MLIR Toy Tutorial 和 MLIR Dialect 文档重绘。箭头表示语义逐步 Lower，不代表所有项目都经过完全相同的 Dialect。*

以矩阵乘加为例，高层只关心“做什么”：

```mlir
%0 = "toy.matmul"(%a, %b)
     : (tensor<128x64xf32>, tensor<64x128xf32>)
       -> tensor<128x128xf32>
%1 = "toy.add"(%0, %bias)
     : (tensor<128x128xf32>, tensor<128x128xf32>)
       -> tensor<128x128xf32>
```

降到结构化算子层后，会显式出现输入、输出和迭代语义：

```mlir
%0 = linalg.matmul
     ins(%a, %b : tensor<128x64xf32>, tensor<64x128xf32>)
     outs(%init : tensor<128x128xf32>)
```

再往下可能出现循环、向量、GPU 或 LLVM 操作：

```text
linalg.matmul
  -> scf.for / affine.for
  -> vector.contract
  -> gpu.launch + gpu.thread_id
  -> nvvm / llvm
  -> PTX / object code
```

高层 IR 容易做算子融合与形状推断；低层 IR 容易控制线程、内存和具体指令。多层 IR 的价值是让优化发生在“信息还没丢”的正确层次。

## 3. Operation 与 Dialect

MLIR 中很多东西都统一表示为 Operation。一个 operation 可以拥有：

- 操作名，例如 `arith.addf`、`tensor.cast`、`gpu.launch`；
- 输入 operand 和输出 result；
- attribute，例如维度、常量或配置；
- region 与 block，用于嵌套控制流；
- trait/interface，用于声明可验证或可复用的行为。

操作名的前缀通常就是 Dialect。以下几组并不处在同一抽象层：

| Dialect | 保留的信息 | 常见用途 |
| --- | --- | --- |
| `tensor` | ranked/unranked tensor、切片与形状 | 张量结构变换 |
| `linalg` | 结构化线性代数迭代语义 | 融合、tile、vectorize |
| `scf` / `affine` | 循环与控制流 | 循环变换、依赖分析 |
| `vector` | SIMD/向量操作 | 向量化与硬件映射前准备 |
| `gpu` | grid、block、thread、memory space | 通用 GPU 映射 |
| `nvvm` / `llvm` | 接近后端 intrinsic 与 ABI | 生成目标代码 |

自定义 Dialect 的意义不是换一套语法，而是让编译器在一段时间内保留领域语义。例如“这是 attention”比“一串循环和 load/store”更容易做模式级替换。

## 4. Pass、Rewrite 与 Conversion

这三个词经常混用，但职责不同。

### 4.1 Pass 是执行变换的容器

Pass 可以在 module、function 或 operation 层运行，做分析或修改。例如 canonicalization、CSE、shape inference、fusion 都可以组织为 pass。

### 4.2 Rewrite 描述局部替换

Rewrite Pattern 匹配一段 IR，再把它替换为等价但更规范或更高效的形式：

```text
transpose(transpose(x))  ->  x
add(x, 0)                ->  x
reshape(reshape(x))      ->  reshape(x)
```

Canonicalization 通常会反复应用这些局部规则，直到没有可继续改写的模式。

### 4.3 Conversion 改变合法操作集合

Conversion 会定义目标层允许哪些 operation，并为非法 operation 提供 lowering pattern。例如目标只允许 `arith`、`scf` 和 `memref`，那么剩余 `toy.*` 操作必须全部转换或报告失败。

这种“合法性驱动”很重要：它让编译失败暴露尚未覆盖的语义，而不是悄悄留下后端不认识的操作。

## 5. Lowering 如何逐层发生

完整 lowering 通常不是一次巨大的替换，而是一串边界清晰的阶段：

1. **高层规范化**：常量折叠、冗余 reshape/transpose 消除、形状推断；
2. **结构化张量计算**：转到 `linalg`、`tensor` 等仍保留迭代语义的 Dialect；
3. **Bufferization**：把不可变 tensor 值语义转换为显式 buffer/memref；
4. **循环与向量化**：tile、分发循环、生成 vector 操作；
5. **设备映射**：决定 GPU grid/block/thread 和 memory space；
6. **后端 lowering**：转到 NVVM/LLVM 或其他目标后端。

每一步都要回答两个问题：转换前后哪些语义保持不变？下一层新增了哪些实现约束？如果只看最终 PTX，很难判断性能问题是在哪个阶段引入的。

## 6. 跟随 Toy Tutorial 动手

Toy Tutorial 的价值在于它让你亲手补齐一条小编译链。建议每章都保存输入和输出 IR：

| Toy 章节 | 重点 | 建议观察 |
| --- | --- | --- |
| Chapter 1 | AST 与语言前端 | 源代码信息怎样进入 AST |
| Chapter 2 | 定义 Toy Dialect | operation/type/verification |
| Chapter 3 | 高层变换 | shape inference 与 pattern rewrite |
| Chapter 4 | Generic Call | interface 与可扩展调用 |
| Chapter 5 | Partial Lowering | Toy 与 Affine 混合存在 |
| Chapter 6 | LLVM Lowering | buffer、ABI 与目标代码 |

不要只复制最终代码。每一步至少保留一次 `mlir-opt` 或教程驱动程序打印的 IR diff，并写下：

1. 哪个 operation 消失了；
2. 哪个 Dialect 的 operation 新出现了；
3. shape/layout 信息是否还存在；
4. 这一步之后还能否做算子级融合；
5. 如果结果错了，最早从哪一层开始不同。

## 7. 怎样阅读真实项目的 MLIR

真实项目的 pass pipeline 很长，可以用固定方法缩小范围：

1. 从前端输出中找你关心的算子或函数；
2. 开启 IR dump，只保留该函数；
3. 在每次主要 dialect conversion 前后保存快照；
4. 搜索第一个出现 layout、tile 或 memory space 的位置；
5. 再去读对应 pass 的实现和选项。

阅读时不要把 operation 名当作性能结论。`linalg.matmul` 还没有说明 tile 大小，`gpu.launch` 也没有说明访存一定合并；必须继续看属性、循环边界、索引和生成代码。

## 8. MLIR 与 Triton、TVM、XLA 的关系

| 名称 | 更准确的定位 |
| --- | --- |
| MLIR | 构建多层 IR 与编译流水线的基础设施 |
| Triton | 面向 GPU block-level kernel 的语言与编译器 |
| TorchInductor | PyTorch 图的编译后端，可生成 Triton/C++ 等代码 |
| TVM | 覆盖模型 IR、TensorIR、调度、代码生成和运行时的编译栈 |
| XLA | 面向 HLO 图的编译器，服务 JAX/TF 等前端与多种后端 |

这些项目不是简单互斥。一个系统可以使用 MLIR 基础设施表达多层 IR，也可以在某一阶段生成 Triton kernel，或通过 StableHLO 与另一套编译器交换模型语义。

## 9. 常见错误

### 9.1 把 MLIR 当作单一 IR

MLIR 的关键恰恰是多个 Dialect 和层次。问“MLIR 长什么样”不如问“当前是哪组 Dialect、处在 pipeline 哪一层”。

### 9.2 一开始就读所有 Dialect 文档

先走通 Toy，再只读当前流水线实际出现的 Dialect。脱离可运行例子背接口很难建立层次感。

### 9.3 过早 Lower 到低层

降成循环和地址计算后，高层算子与布局语义很难恢复。融合、形状推断和布局传播应尽量在信息仍完整的层次完成。

### 9.4 把“Lower 成功”当成“性能好”

Lowering 只保证可表达和语义正确。tile、向量宽度、线程映射、内存层级和硬件指令仍需通过 profiler 和目标代码验证。

## 总结

- MLIR 是多层编译器基础设施，不是固定的模型优化器。
- Dialect 保存某一层需要的语义；Pass/Rewrite 优化当前层；Conversion 改变合法操作集合并推动 Lowering。
- 学习重点是追踪信息如何保留或消失，而不是背 IR 语法。
- Toy Tutorial 是最完整的入门主线；真实项目中应围绕目标函数和关键 conversion 缩小阅读范围。
