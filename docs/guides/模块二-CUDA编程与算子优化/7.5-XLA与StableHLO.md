## 主教程

XLA 官方目前没有一套与 MLIR Toy 同等完整、从零实现编译器的初学者教程。最易运行的入口是 JAX 官方 [Just-in-time compilation](https://docs.jax.dev/en/latest/jit-compilation.html) 和 [Ahead-of-time lowering and compilation](https://docs.jax.dev/en/latest/aot.html)：先观察 tracing 与 `jit`，再用 `lower()`、`compile()` 查看编译阶段。

建立可运行流程后，再读 [OpenXLA: XLA architecture](https://openxla.org/xla/architecture) 理解前端、HLO pass 与后端；[StableHLO Specification](https://openxla.org/stablehlo/spec) 只用于核对 operation 语义，不作为第一篇教程。当前网络若无法访问 OpenXLA，应保留这些官方入口，但不要把未打开过的规范内容写成已实测结论。

本站补的是一条顺读路径：Python 程序怎样被 trace，怎样进入 StableHLO/HLO，XLA 在哪一层做融合和布局，最后怎样确认实际生成的执行路径。

## 1. XLA 在编译链中的位置

XLA 接收线性代数风格的程序图，运行一系列 HLO 优化，再交给 CPU、GPU、TPU 等后端生成可执行文件。它关注的不只是单个 kernel，还包括：

- 图级常量传播、死代码消除和算子融合；
- shape 与 layout 的传播；
- buffer 分配与复用；
- collective communication 的表示和调度；
- 面向不同设备的代码生成与库调用。

这和 Triton 的视角不同。Triton 让开发者直接表达一个 block-level GPU kernel；XLA 通常从完整函数或计算图出发，决定哪些部分融合成 kernel、哪些调用高性能库、哪些跨设备执行。

## 2. JAX 程序如何进入编译器

JAX 会先 trace Python 函数，把对数组的计算记录成更受限制的中间程序。可以先看 jaxpr：

```python
import jax
import jax.numpy as jnp

def f(x, bias):
    y = x * 2.0 + bias
    return jax.nn.relu(y)

x = jnp.ones((8,), dtype=jnp.float32)
bias = jnp.arange(8, dtype=jnp.float32)

print(jax.make_jaxpr(f)(x, bias))
```

jaxpr 已经不是任意 Python。数据依赖的 Python 分支、动态列表操作或带副作用的代码，可能无法按你预期被 trace。要理解 `jit`，先理解哪些值在 trace 时是抽象值，哪些值必须是静态参数。

## 3. StableHLO 与 HLO 分别是什么

StableHLO 是带稳定性与兼容目标的 operation set，用于在机器学习框架和编译器之间交换程序；XLA 内部 HLO 则可以继续采用更贴近其优化和后端需求的表示。

不要把二者简单理解成“同一个文本格式的两个名字”。实际流水线更接近：

```text
JAX / TensorFlow / PyTorch frontend
             ↓
      StableHLO-like exchange IR
             ↓
       XLA HLO optimizations
             ↓
     CPU / GPU / TPU backend
```

StableHLO 规范回答 operation 的输入、输出、属性和语义；它不保证某个 operation 最终一定对应一个 kernel。例如多个逐元素 operation 可能被融合成一个 kernel，dot/convolution 也可能转成库调用。

## 4. 从程序图到设备代码

![JAX、StableHLO、XLA HLO 与设备后端的编译路径](/AIInfraGuide/images/cuda-optimization/xla-stablehlo-flow.svg)

*图：本站据 JAX AOT 文档与 OpenXLA 架构说明重绘。实际 pass 名称和先后顺序会随前端、后端和版本变化。*

可把流程分成四个观察点：

1. **Tracing / jaxpr**：Python 结构是否被捕获，静态参数和 shape 是什么；
2. **Lowered IR**：StableHLO/HLO 中有哪些 operation，常量和广播如何表达；
3. **Optimized HLO**：哪些 operation 被融合、重排或替换为库调用；
4. **Executable / profile**：最终有多少 kernel、库调用、数据传输和同步。

若结果慢，先找到变化发生在哪一层。图中已经融合但 GPU 仍慢，问题可能是 kernel 形状或内存访问；图在 tracing 阶段就被切碎，则应先修复前端控制流或静态参数。

## 5. 用一个最小例子查看 IR

JAX 的具体文本格式和 dialect 参数会随版本变化，下面的模式比固定输出文本更重要：

```python
import jax
import jax.numpy as jnp

@jax.jit
def fused_candidate(x, bias):
    return jax.nn.gelu(x * 0.5 + bias)

x = jnp.ones((1024, 1024), dtype=jnp.float16)
bias = jnp.ones((1024,), dtype=jnp.float16)

lowered = fused_candidate.lower(x, bias)
print(lowered.as_text())

compiled = lowered.compile()
y = compiled(x, bias)
y.block_until_ready()
```

实验时保存三样东西：

- `jax.make_jaxpr` 输出；
- `lowered.as_text()` 输出；
- profiler 中的 kernel/库调用列表。

不要仅凭函数名 `fused_candidate` 推断已经融合。只有 IR 或 profiler 能确认。

## 6. 融合、布局与形状

### 6.1 融合

逐元素链通常有很强的融合机会，因为中间张量可以留在寄存器或一个 kernel 内。但融合也有边界：复杂 reduction、不同 layout、跨设备操作、复用关系或过高寄存器压力都可能改变决策。

### 6.2 布局

HLO 的逻辑 shape 不等于物理内存布局。后端需要决定维度顺序、tile 和库调用所需格式；必要时会插入 transpose/copy。一个数学上多余的布局转换可能成为显著开销，所以要在 optimized HLO 和时间线中检查真实 copy。

### 6.3 静态与动态形状

稳定 shape 给编译器更多常量传播、内存规划和专用 kernel 机会。动态 batch/sequence 并不意味着无法编译，但可能导致：

- 多版本编译或重新编译；
- 更保守的边界判断；
- 难以固定 tile 或 buffer 大小；
- 编译缓存命中率下降。

## 7. 编译缓存与动态输入

`jit` 的首次调用包含 tracing、lowering、编译和加载。性能测试必须把首次编译与稳态执行分开：

```python
import time

t0 = time.perf_counter()
y = fused_candidate(x, bias)
y.block_until_ready()
compile_and_first_run = time.perf_counter() - t0

for _ in range(10):
    fused_candidate(x, bias).block_until_ready()

t0 = time.perf_counter()
for _ in range(100):
    y = fused_candidate(x, bias)
y.block_until_ready()
steady = (time.perf_counter() - t0) / 100
```

改变 shape、dtype 或静态参数可能生成新编译项。实验中要记录调用序列，而不是只记录“平均 100 次”，否则重新编译和缓存命中会被混在一起。

## 8. 什么时候使用 XLA

XLA 更适合：

- JAX/TPU 工作负载；
- 希望编译完整函数或计算图，而不是只写一个 kernel；
- 需要让融合、布局、buffer 规划和 collective 在统一图中优化；
- shape 相对稳定，或可以通过分桶管理动态 shape；
- 能接受编译缓存与前端约束。

若目标是 PyTorch 内单个 NVIDIA GPU 自定义算子，Triton/CUDA 可能更直接；若要建立可编程 schedule 和跨硬件部署栈，可以评估 TVM；若在搭建新的多层编译器，MLIR 提供基础设施。选型取决于入口生态和控制层次。

## 9. 常见错误

### 9.1 把 `jax.jit` 的首次时间当执行时间

首次调用包含编译。必须 `block_until_ready()`，并分别报告首次与稳态时间。

### 9.2 把 StableHLO operation 数当 kernel 数

后端可能融合多个 operation，也可能为一个高层 operation 生成多个 kernel 或库调用。最终以 executable 和 profiler 为准。

### 9.3 忽略异步执行

JAX 在加速器上通常异步 dispatch。没有等待结果就停止计时，会只测到提交时间。

### 9.4 把所有动态 shape 都当成同一种问题

动态 batch、动态序列长度、数据依赖控制流对编译的影响不同。要观察具体 guard、重编译次数和生成 IR，不能只贴“dynamic”标签。

### 9.5 用 StableHLO 规范当入门教程

规范适合查证 operation 语义，不负责解释 tracing、编译缓存和 profiler。初学先跑 JAX JIT/AOT 教程，再查规范。

## 总结

- XLA 从完整计算图出发，在 HLO 层做融合、布局、buffer 与后端优化。
- JAX 的 jaxpr、lowered IR、optimized HLO 和 profiler 是四个不同观察点。
- StableHLO 提供较稳定的交换语义，但 operation 数不等于最终 kernel 数。
- 性能实验必须区分编译与稳态执行，并显式等待异步设备完成。
