## 建议先读

[vLLM Production Stack 介绍](https://vllm.ai/blog/2025-01-21-stack-release) 把 Prometheus/Grafana 放在完整服务架构中，适合先理解观测组件为何存在。随后再查具体指标与 OpenTelemetry 约定。

## 三类信号分工

| 信号 | 适合回答 | 不适合承载 |
| --- | --- | --- |
| Metrics | 趋势、SLO、告警 | 原始 prompt、request ID |
| Logs | 错误详情、事件、审计 | 高频逐 token 全量数据 |
| Traces | 单请求跨组件时序 | 长期聚合趋势 |

同一请求应能从入口 trace 到队列、Prefill、Decode、工具调用和返回，并在错误日志中保留 trace/request ID。

## 三层看板

1. **用户层**：请求率、错误率、TTFT/TPOT/E2E p50/p95/p99、goodput。
2. **引擎层**：waiting/running tokens、KV 使用、Prefix Cache 命中、batch 大小、抢占。
3. **资源层**：GPU 利用率/显存/功耗、CPU、网络、磁盘与 NCCL。

告警应从用户 SLO 触发，再用引擎和资源层定位；只对 GPU utilization 告警既不稳定，也不能说明用户是否受影响。

## 标签与隐私

Metrics 标签使用模型族、版本、状态码、实例和有限的请求类型。用户 ID、request ID、prompt、URL 和任意 Adapter 名会造成高基数或泄密，应进入受控日志/trace，并有采样、脱敏和保留期限。
