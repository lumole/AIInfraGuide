V1 不是给 V0 增加几个参数，而是重新组织 CPU 与 GPU 的关键路径。学习时应分别看进程边界、调度抽象、KV/Prefix Cache 和 ModelRunner 输入更新。

## 主教程

[vLLM V1：A Major Upgrade to vLLM's Core Architecture](https://blog.vllm.ai/2025/01/27/v1-alpha-release.html) 用架构图和 benchmark 解释重构动机，是本节主线。先读博客，再用 [V1 Design](https://docs.vllm.ai/en/latest/design/v1/) 核对当前实现；博客性能数字只代表原测试环境。

## 1. 为什么把 EngineCore 隔离出来

API、tokenization、detokenization 和网络流式响应都在 CPU 上运行。若它们与核心调度循环串在同一进程，CPU 工作会推迟下一次 GPU launch。V1 用进程边界让前后处理与 EngineCore 重叠，并缩小关键循环职责。

## 2. 统一 token 调度

传统描述把 Prefill 和 Decode 当成两类请求。V1 调度器更统一地记录请求已计算 token 数与目标 token 数，本轮为每个请求分配 num_scheduled_tokens。长 Prefill 可以只拿部分预算，Decode 每轮通常拿一个或少量 token。

这样 Chunked Prefill 不再是旁路功能，Prefix Cache 命中也可以直接反映为“已经计算的 token”。调度器仍需选择优先级，但核心资源单位统一为 token budget。

## 3. Prefix Cache 为什么更接近零开销

KV block 的完整 token 序列可作为内容哈希的一部分。调度请求时，KVCacheManager 查询命中的连续前缀，并只为剩余 token 分配新块。未命中请求主要多一次哈希/查询，不必走独立执行路径。

零开销是相对旧设计的架构目标，不代表缓存没有内存、哈希和驱逐成本。跨 LoRA、模型 revision、multi-modal 输入或不同 cache salt 时，cache key 必须隔离。

## 4. Persistent Batch

如果每个 step 都从 CPU 重建整个 batch 并把完整 metadata 复制到 GPU，Decode 的小计算容易被输入准备开销淹没。Persistent Batch 在 ModelRunner 中保留稳定槽位，只对新增、完成或变化请求更新 diff。

代价是状态管理更复杂：请求槽位、block table、采样参数和完成回收必须一致。调试时要区分 Scheduler 的逻辑 batch 与 GPUModelRunner 的持久化表示。

## 5. CUDA Graph 与动态请求

Persistent Batch 为更稳定的 shape 和 CUDA Graph replay 创造条件，但在线请求仍然动态变化。实现会使用预先捕获的 batch size、padding 或 eager fallback。配置更大 graph 覆盖范围会增加显存；命中率低时收益有限。

## 6. V0 与 V1 比较时要固定什么

必须固定模型、dtype、Attention backend、并行度、输入/输出分布、并发/请求率、采样和硬件。比较 TTFT、TPOT、goodput、CPU 占用、GPU gap 与显存，不能只引用博客中的总体吞吐倍率。

## 7. 阅读顺序

1. 先画进程与消息边界。
2. 跟踪 EngineCore 主循环的一轮 schedule/execute/update。
3. 看 SchedulerOutput 包含哪些增量信息。
4. 看 GPUModelRunner 如何更新 persistent batch。
5. 最后再进入 CUDA Graph 与 Attention backend。
