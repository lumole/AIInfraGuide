理解 vLLM 最有效的方法不是背类名，而是跟踪一次请求：文本在哪里被 tokenize，何时进入调度队列，KV block 何时分配，GPU 前向怎样执行，采样结果又如何返回。

## 阅读入口

先读 [vLLM V1 架构文档](https://docs.vllm.ai/en/latest/design/v1/) 的 overview，把本页当中文路线图。类名和进程边界会随版本变化，实际阅读源码时固定 git commit；本文只讲稳定职责。

## 1. 从 API 到 EngineCore

在线请求由 API server 完成协议解析、认证和 chat template，再交给 engine client。tokenization 可以在核心执行循环之外完成，避免阻塞 GPU 调度。

~~~mermaid
flowchart LR
    API["OpenAI-compatible API"] --> PARSE["请求校验 / Chat Template"]
    PARSE --> TOK["Tokenizer"]
    TOK --> CLIENT["Engine Client"]
    CLIENT --> CORE["EngineCore"]
    CORE --> SCHED["Scheduler"]
    SCHED --> KV["KVCacheManager"]
    SCHED --> EXEC["Executor / Worker"]
    EXEC --> RUNNER["ModelRunner"]
    RUNNER --> GPU["Attention / MLP / Sampling"]
    GPU --> OUT["Detokenize / Stream"]
~~~

API 层关心 HTTP 与用户语义；EngineCore 关心 token、调度、KV 与模型执行。分开进程后，两侧通过消息传递交换请求与增量输出。

## 2. 请求状态

请求进入后通常先位于 waiting 队列。Scheduler 为它分配本 step 的 token budget 与 KV block 后进入 running。每轮执行结束，调度器更新已计算 token、输出、停止条件和 KV 状态；完成或取消后释放资源。

~~~mermaid
flowchart LR
    START["请求进入"] --> WAIT["Waiting"]
    WAIT -->|"分配 token budget 与 KV"| RUN["Running"]
    RUN -->|"仍未结束"| RUN
    RUN -->|"抢占 / 重新调度"| WAIT
    RUN -->|"EOS / stop / 长度上限"| FIN["Finished"]
    WAIT -->|"取消 / 拒绝"| FIN
    FIN --> FREE["释放 KV 与请求状态"]
~~~

这里的 running 不等于“独占 GPU”。多个请求会被放入同一 iteration batch，共同执行本轮 token。

## 3. Scheduler 做什么

Scheduler 根据全局 token budget、KV 可用块、请求优先级和缓存命中，决定每个请求本轮计算多少 token。V1 将 Prefill 与 Decode 统一成“还需要计算多少 token”，因此 Chunked Prefill、Prefix Cache 和普通 Decode 可以在同一预算内调度。

调度输出不是模型结果，而是一份执行计划：哪些请求、每个请求计算多少 token、使用哪些 KV block、哪些请求需要抢占或释放。

## 4. KVCacheManager 做什么

KVCacheManager 管理逻辑 token 到物理 block 的映射、分配、释放、引用计数与 prefix 命中。Scheduler 决定“谁能运行”，KVCacheManager 回答“是否有空间以及 block 在哪里”。

当 Prefix Cache 命中时，已缓存 token 不需再次执行模型，但请求仍要从命中边界继续分配 KV。取消、抢占和完成必须正确释放引用，不能留下悬挂 block。

## 5. Worker 与 ModelRunner

Executor 把执行计划发送给本地或分布式 worker。每个 worker 负责对应设备/rank；ModelRunner 准备输入张量、block table、position 和 sampling metadata，维护 persistent batch，并调用模型与 Attention backend。

分布式 TP 下，每个 rank 执行同一请求的权重分片；只有特定 rank 或后处理阶段负责合并 logits、采样与输出。进程多不代表请求被复制多次。

## 6. 一轮 step

~~~mermaid
sequenceDiagram
    participant C as EngineCore
    participant S as Scheduler
    participant K as KVCacheManager
    participant W as Worker/ModelRunner
    C->>S: schedule()
    S->>K: 查询命中并分配 blocks
    K-->>S: block tables
    S->>W: SchedulerOutput
    W->>W: 更新 persistent batch
    W->>W: GPU forward + sample
    W-->>C: sampled tokens / states
    C->>S: 更新请求与完成状态
~~~

性能分析时也按这条链路定位：queue time 看 Scheduler 前后，CPU gap 看 EngineCore/ModelRunner，KV 异常看 block 管理，GPU 时间再看 Attention/MLP kernel。

## 7. 版本化源码阅读

固定 commit 后，从 API server 的请求入口追到 engine client，再读 EngineCore 主循环、Scheduler.schedule、KVCacheManager 和 GPUModelRunner。每次只跟踪一个最小 greedy 请求，并在 waiting/running、scheduled token 和 block table 处打印或断点，避免一开始遍历整个仓库。
