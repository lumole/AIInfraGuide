参数名称很多，但调优目标只有几类：模型能否装下、一次允许多少 token、同时保留多少请求、哪些 shape 命中高效执行路径。按资源约束调参数，比从参数表逐项尝试更可靠。

## 阅读入口

先读 [vLLM Optimization and Tuning](https://docs.vllm.ai/en/latest/configuration/optimization/) 的完整流程，再用 [Engine Arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/) 核对当前字段。官方页面是操作依据，本页负责解释参数之间的因果关系。

## 1. 先建立不调参基线

固定模型 revision、dtype/量化、GPU、vLLM 版本、输入/输出分布和采样。记录 TTFT、TPOT、goodput、峰值显存、KV 使用和错误。没有基线时，多个参数同时变化无法归因。

## 2. 显存相关

gpu_memory_utilization 决定引擎可使用的显存预算；max_model_len 影响单请求最大 KV；max_num_seqs 影响同时驻留请求；CUDA Graph 和 workspace 也占显存。

~~~mermaid
flowchart TD
    OOM["OOM 或可服务并发不足"] --> FIXED{"权重/固定开销过大?"}
    FIXED -->|是| Q["量化 / TP / 更小模型"]
    FIXED -->|否| KV{"KV 是主因?"}
    KV -->|是| LEN["降低 max_model_len 或并发<br/>考虑 KV 量化"]
    KV -->|否| GRAPH["检查 graph/workspace/碎片"]
~~~

不要把 gpu_memory_utilization 一直调到接近 1。驱动、NCCL、临时 kernel 与流量波动需要余量。

## 3. Token Budget

max_num_batched_tokens 控制一轮可调度 token。增大它可提高大 Prefill 吞吐，却可能让 Decode 等待更久并增加 activation/workspace。Chunked Prefill 把长 prompt 切分后，budget 同时决定 chunk 大小与 Decode 插入机会。

调优时分别观察 TTFT、TPOT 与 output tokens/s；只看总吞吐容易掩盖交互延迟退化。

## 4. 并发

max_num_seqs 是同时参与调度的请求上限，不等于入口最大连接数。过低会浪费 batching，过高会增加 KV 压力、排队复杂度和抢占。最佳值取决于长度分布、SLO 与显存，而不是 GPU 型号固定表。

## 5. CUDA Graph 与 eager

CUDA Graph 可减少 launch 开销，但需要可捕获 shape 和额外内存。强制 eager 适合调试和不支持 graph 的路径；生产应比较 graph replay 命中、显存和 TPOT，而不是默认“graph 一定更快”。

## 6. Attention Backend

backend 选择受 GPU 架构、dtype、head dimension、滑窗/MLA、KV dtype 和软件版本影响。显式指定前先确认兼容；出现性能异常时用日志与 profiler 证明实际命中的 kernel。

## 7. 推荐实验顺序

1. 固定模型能运行的最小配置。
2. 设定真实 max_model_len 与显存余量。
3. 扫 max_num_batched_tokens，画 TTFT/TPOT/吞吐曲线。
4. 在选定 budget 下扫 max_num_seqs。
5. 比较 graph/eager 与 backend。
6. 最后再叠加 Prefix Cache、量化或投机解码。
