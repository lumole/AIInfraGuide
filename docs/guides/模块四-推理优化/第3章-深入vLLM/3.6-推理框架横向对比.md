没有一篇中立教程能长期覆盖三个快速演进的框架。本文不替它们下永久结论，而是基于各自一手资料给出公平比较方法；功能支持与性能必须在同一时间、同一环境重新核对。

## 1. 先排除不满足硬约束的候选

列出模型架构、GPU、量化格式、最大上下文、结构化输出、工具调用、多模态、LoRA、并行、API 与许可证要求。任何必需项不支持，就不进入性能比较。

## 2. 三个框架的设计重心

| 框架 | 阅读入口 | 常见设计重心 | 重点核对 |
| --- | --- | --- | --- |
| vLLM | [V1 Design](https://docs.vllm.ai/en/latest/design/v1/) | 通用 serving、分页 KV、连续调度、生态 | 功能兼容、版本变化、目标 kernel |
| SGLang | [SGLang Docs](https://docs.sglang.ai/) | RadixAttention、前端语言/Agent、结构化与高性能 runtime | Prefix 负载、模型与 parser 支持 |
| TensorRT-LLM | [Architecture](https://nvidia.github.io/TensorRT-LLM/architecture/overview.html) | NVIDIA GPU 深度优化、engine 构建与多种低精度路径 | 构建成本、GPU/精度支持、运维流程 |

这不是性能排名。相同框架在不同模型、GPU、batch 和功能组合下会改变结果。

## 3. 公平基线

使用同一模型 revision、tokenizer/template、精度、最大长度、输入/输出分布、并发/到达率、采样、质量集和硬件。若某框架必须使用不同量化或 engine build，应把它作为单独方案，并明确质量差异。

## 4. 功能正确性先于吞吐

逐项验证流式、取消、stop、usage/logprobs、结构化输出、工具、多模态、LoRA、Prefix Cache 与错误语义。一个框架若因缺少业务必需能力而需要外部复杂补丁，其集成成本必须计入选型。

## 5. 性能比较

~~~mermaid
flowchart LR
    COR["同一正确性/质量门槛"] --> LOW["低并发: TTFT/TPOT"]
    LOW --> CURVE["扫并发/到达率"]
    CURVE --> GOOD["SLO 内 Goodput"]
    GOOD --> COST["显存、GPU 与成本"]
    COST --> OPS["启动、扩缩容、观测、回滚"]
~~~

不要只比较一个峰值点。至少画延迟-吞吐曲线，报告 p95/p99、峰值显存、冷启动、错误率和成本/1M good tokens。

## 6. 运维与团队成本

评估镜像和依赖、模型/engine 构建时间、可观测、升级频率、故障定位、社区/商业支持和团队熟悉度。极限性能高但每次模型升级都需长时间构建与验证，可能不适合快速迭代业务。

## 7. 结论如何写

写成“在 H100、模型 X revision Y、输入/输出分布 Z、功能集 F 下，候选 A 的 SLO goodput/成本更好”，不要写成“框架 A 永远比 B 快”。附 manifest、原始数据和三方版本，设定下次重测条件。
