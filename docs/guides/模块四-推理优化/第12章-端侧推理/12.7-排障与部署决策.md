各 Runtime 的 troubleshooting 只覆盖自家日志，没有一篇适合初学者的跨 Runtime 故障树。本页按导出、精度、backend、首次运行和热退化的顺序整理。

## 1. 导出失败

先缩小到最小失败输入，定位不支持的 Python 控制流、动态 shape、自定义算子或 state。分别验证 eager、图捕获与变换阶段，避免把所有错误都归给设备 backend。

~~~mermaid
flowchart TD
    F["失败或性能异常"] --> E{"导出图能否运行?"}
    E -->|否| EXPORT["缩小到算子/shape/控制流"]
    E -->|是| A{"数值是否一致?"}
    A -->|否| ACC["逐阶段比较 eager/export/lowered/device"]
    A -->|是| B{"目标 backend 是否接管?"}
    B -->|否| FALL["检查 unsupported op 与 fallback"]
    B -->|是| T{"仅首轮慢还是持续变慢?"}
    T -->|首轮| COLD["编译、cache、加载、内存页"]
    T -->|持续| HOT["温度、频率、泄漏、后台竞争"]
~~~

## 2. 精度不一致

固定输入和 seed，逐阶段保存中间输出；先比较 FP 基线，再加入量化。定位第一个误差放大的节点，并检查 layout、dtype、scale/zero point、预处理和后处理。不要只比较最终自然语言文本。

## 3. NPU/GPU 比 CPU 慢

查看 partition 结果，而非只看“已启用 delegate”。可能原因包括子图太小、fallback 过多、边界搬运、首次编译、动态 shape 或 CPU 已有更合适的优化 kernel。分别报告 backend 执行和端到端时间。

## 4. 首次运行慢

区分文件读取/映射、runtime 初始化、backend 编译、权重重排与 cache 建立。若允许预热，明确预热发生在安装、启动还是首请求；不要用热启动数字宣传冷启动体验。

## 5. 越跑越慢

同时采样温度、CPU/GPU/NPU 频率、功耗、内存和后台状态。性能随温度下降通常是热降频；内存持续增长则优先查缓存/资源释放；随机抖动还可能来自 OS 调度。

## 6. 部署决策

只有当候选在最低目标设备上满足质量、冷启动、稳态速度、峰值内存、功耗/热和 App 生命周期，才进入发布。若 delegate 只在少量高端设备有效，应保留 CPU 路径并按设备能力选择，而不是一刀切。
