## 建议先读

先读 [AWS DPD 教程](https://aws.amazon.com/cn/blogs/machine-learning/disaggregated-prefill-and-decode-for-llm-inference-on-sagemaker-hyperpod/) 的架构与 EFA/RDMA 部分。它能建立完整数据路径；本页再把不同实现中的术语统一起来。

## 传输的不只是张量

Decode worker 需要确认 KV 对应的模型、层、请求、token 区间、dtype、布局、TP rank 和目标 block。只传一块裸显存无法安全恢复请求。

| 对象 | 内容 |
| --- | --- |
| 请求身份 | request ID、模型 revision、Adapter/多模态上下文 |
| token 范围 | 已计算 prefix 长度、块边界、位置编码状态 |
| 张量描述 | layer、K/V、shape、dtype、layout、rank |
| 目标位置 | Decode 侧 block/slot 映射 |
| 完成状态 | 已发布、已确认、超时、取消、失败 |

~~~mermaid
sequenceDiagram
    participant R as Router
    participant P as Prefill worker
    participant C as KV Connector
    participant D as Decode worker
    R->>D: 预留请求与 KV 空间
    R->>P: 执行 Prefill
    P->>C: 发布 KV + 元数据
    C->>D: RDMA / P2P / storage transfer
    D-->>C: 校验并确认可见
    C-->>R: KV ready
    R->>D: 开始 Decode
~~~

先在 Decode 侧预留空间可以避免数据到达后无处写入；何时对调度器宣布 KV ready，决定了 Decode 是否会读到未完成数据。

## Connector 与传输层不是一回事

Connector 管理请求生命周期、元数据、block 映射和完成通知；NIXL、RDMA、共享内存或存储系统负责搬运字节。NVIDIA Dynamo、vLLM 和 Mooncake 对模块命名不同，但都要解决“描述什么、传到哪里、何时可见、失败怎么办”。

## TP 与布局

Prefill/Decode 的 TP 规模相同，KV 可按 rank 对 rank 传输。若并行度或 layout 不同，就需要重分片、转置或聚合，网络量和中间 buffer 都会增加。部署前应明确：

- K/V 每层每 token 的字节数；
- block size 与目标分页格式；
- Prefill rank 到 Decode rank 的映射；
- 传输能否与后续层或请求重叠；
- 取消请求时如何回收两侧空间。

## 失败语义

KV 传输失败不能让 Decode 从空块继续生成。可选策略是重试传输、重新 Prefill、回退到统一 worker 或终止请求。每种策略都要有超时、幂等 request ID 和显存回收规则。
