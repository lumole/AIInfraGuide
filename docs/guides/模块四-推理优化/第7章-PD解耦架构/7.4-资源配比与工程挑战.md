解耦后不能凭经验写一个固定 P:D 比例。输入/输出长度、到达率、模型并行度、网络和 SLO 一变，比例就会变化。本页给出可填数据的最小计算过程。

## 1. 对真实流量分桶

至少按输入和输出 token 把请求分为四类，并为每类记录到达率 $lambda_j$、Prefill 平均服务时间 $s_{p,j}$、Decode 占用时间 $s_{d,j}$ 与 KV 字节数 $b_j$。

不要只用全局平均。长 prompt 对 Prefill 压力大，长输出则长期占用 Decode；平均值会隐藏两个池的峰值。

## 2. 计算基础负载

Prefill 与 Decode 的平均并发工作量近似为：

$$
L_p=\sum_j \lambda_j s_{p,j},\qquad
L_d=\sum_j \lambda_j s_{d,j}
$$

若一个 Prefill worker 在目标 SLO 下可承载有效并发 $c_p$，基础数量近似为：

$$
N_p=\left\lceil \frac{L_p}{c_p u_p}\right\rceil
$$

$u_p$ 是目标利用率上限，用于保留排队和突发余量。Decode 同理。$c_p$ 与 $c_d$ 不能凭峰值 tokens/s 推出，应由固定负载压测得到。

## 3. 网络是第三个容量池

平均 KV 带宽需求为：

$$
B_{kv}=\sum_j \lambda_j b_j
$$

还要检查突发带宽与并发传输数。网络达到平均可承载并不代表尾延迟可控；若多个长 prompt 同时完成 Prefill，KV 突发可能让 Decode 空等。

KV 大小应按实际 GQA/MQA、层数、head dimension、dtype、token 数和 TP 布局计算，并加入协议元数据、重试与中间 buffer。

## 5. 用压测校准，而不是相信公式

公式只给初始规模。实际系统存在 batching、非线性排队、长度相关 kernel、缓存命中和网络抖动，应按以下顺序校准：

1. 单独压 Prefill 池，得到不同长度/并发下的服务曲线。
2. 单独压 Decode 池，得到 running tokens 与 TPOT 的关系。
3. 单独测 KV 大小与传输 p50/p99。
4. 联调并提高到达率，观察先违反哪个 SLO。
5. 加入一个 worker 故障，验证剩余容量与回退。

## 6. 工程挑战

- 两池模型 revision、量化和 KV layout 必须兼容。
- 扩缩容中的 worker 尚未预热，不能立刻按满容量计算。
- Prefill 完成但 Decode 失败时，必须回收 KV 或重算。
- 网络 buffer、KV staging 和重试会占额外主机/显存。
- 成本应按 goodput 计算，不能按理论 tokens/s 计算。
