## 先读主教程

[AWS DPD 教程](https://aws.amazon.com/cn/blogs/machine-learning/disaggregated-prefill-and-decode-for-llm-inference-on-sagemaker-hyperpod/) 已经用长短请求、架构图和部署过程完整解释了解耦动机。本页不重复文章，只给出读完后应掌握的判断框架。

## 两阶段为何互扰

Prefill 一次处理整段 prompt，矩阵较大，通常偏计算密集；Decode 每步只处理新 token，矩阵较小，更受权重带宽、调度和 kernel launch 影响。统一 batching 能共享权重与 KV 管理，但长 Prefill 若占用太久，会推高正在 Decode 请求的 inter-token latency。

~~~mermaid
sequenceDiagram
    participant Q as 请求队列
    participant G as 统一 GPU
    participant D as 正在 Decode 的请求
    Q->>G: 长 Prompt 进入 Prefill
    G-->>D: Decode iteration 被推迟
    Note over G,D: TTFT 与 TPOT 的资源目标发生冲突
~~~

Chunked Prefill 可以把长 prompt 拆小并与 Decode 交错，先缓解互扰。只有当统一调度仍无法同时满足 TTFT、TPOT 或两阶段设备需求明显不同时，才需要引入解耦。

## 解耦新增了什么

请求先在 Prefill worker 计算 prompt KV，再把 KV 与元数据传给 Decode worker。两池可独立扩缩容和选择并行度，但系统多出 KV 传输、跨池排队、失败恢复、路由状态和额外 GPU 余量。

## 什么时候值得拆

- prompt 长、输出也长，两阶段负载都稳定且可独立规划；
- TTFT 和 TPOT 都有严格、彼此冲突的 SLO；
- 有足够快的节点间链路传 KV；
- Prefill 与 Decode 希望使用不同并行度、GPU 或量化策略；
- 统一调度经 Chunked Prefill 等优化后仍有明显互扰。

## 什么时候不该拆

- 单机或低流量，额外代理与网络成本超过收益；
- prompt 很短，KV 传输固定开销占比高；
- 网络带宽不稳定，Decode 经常等待 KV；
- 团队还不能稳定运营普通多副本服务；
- 目标只是提高平均吞吐，没有独立 TTFT/TPOT 约束。
