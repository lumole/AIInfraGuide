[PyTorch Profiler Recipe](https://docs.pytorch.org/tutorials/recipes/recipes/profiler_recipe.html) 能教会采集与查看 operator profile，但没有覆盖从线上请求到 Nsight kernel 的完整路径。下面依据 PyTorch 与 NVIDIA 一手资料补齐诊断顺序。

## 1. 先确认回归发生在哪一段

~~~mermaid
flowchart TD
    R["延迟或吞吐回归"] --> Q{"queue time 增长?"}
    Q -->|是| ADMIT["先查负载、准入与调度"]
    Q -->|否| P{"TTFT 还是 TPOT?"}
    P -->|TTFT| PRE["Prefill / tokenization / cache"]
    P -->|TPOT| DEC["Decode / scheduling / kernel"]
    PRE --> SYS["系统时间线"]
    DEC --> SYS
    SYS --> K["锁定热点 kernel 后再看 Nsight Compute"]
~~~

不要看到 GPU 利用率低就直接优化 kernel。请求可能在 CPU tokenizer、Python 调度、网络 collective 或队列等待；这时 kernel 级工具无法解释主要损失。

## 2. 请求级证据

保存每个请求的到达、入队、调度、首 token、每个输出 token 和结束时间，并关联模型实例、batch、input/output tokens、Prefix Cache 命中和 KV 使用。先按长度与请求类型分桶，再比较版本。

如果只有整体 p99，没有慢请求的 trace，就无法知道回归是普遍变慢还是少量请求排队。

## 3. 框架级证据

PyTorch Profiler 用于查看 CPU operator、CUDA operator、shape 和内存。短时间、代表性窗口内采集，避免 profiler 本身改变服务行为。关注 CPU self time 与 CUDA time、意外 dtype 转换/拷贝/同步、batch shape、graph break、重新编译和 collective 位置。

## 4. 系统时间线

Nsight Systems 把 CPU thread、CUDA launch、GPU kernel、memcpy 和 NCCL 放在同一时间轴。用它判断 GPU 空隙来自 CPU 未及时 launch 还是通信等待，Prefill/Decode 是否按预期交错，多 rank 是否卡在同一 collective，以及 CUDA Graph 是否真正 replay。

## 5. Kernel 级分析

只有锁定具体热点 kernel 后才使用 Nsight Compute。检查 occupancy、Tensor Core 使用、内存吞吐、warp stall 和访存合并，并与该 shape 的理论目标比较。一次只分析少量 kernel，否则采集成本和数据量都过大。

## 6. 形成可证伪假设

好的结论应写成“Decode 中 CPU 调度间隙从 20us 增至 80us，GPU kernel 本身未变；关闭新增日志后恢复”，而不是“GPU 利用率低，可能是调度”。每个假设都要有单变量实验。
