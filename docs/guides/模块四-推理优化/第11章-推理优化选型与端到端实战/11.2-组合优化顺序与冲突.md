现有综述能分别解释各种优化，但缺少一套可靠的组合顺序。下面依据各功能的一手文档整理；具体兼容性仍必须在同一软件版本上实测。

## 1. 先做基线，再解决硬约束

固定未优化的正确性和性能基线。模型装不下属于硬约束，应先用 TP/PP、量化或更小 context 解决；随后再优化 TTFT/TPOT/吞吐。没有基线就无法知道组合收益来自哪一项。

## 2. 推荐顺序

1. 固定模型、模板、精度和质量集。
2. 选择能稳定运行的 runtime 与最小并行度。
3. 解决显存：权重量化、KV 配置、TP/PP。
4. 优化调度：continuous batching、chunked prefill、token budget。
5. 优化重复工作：Prefix Cache。
6. 针对负载尝试 Speculative Decoding 或 P/D 解耦。
7. 最后做生产路由、扩缩容和成本。

每一步只改一个主要变量，并保留可回退配置。

## 3. 冲突矩阵

| 组合 | 可能冲突 | 必须验证 |
| --- | --- | --- |
| 量化 + TP | packed layout/scale 分片、通信占比上升 | kernel 命中、每 rank 权重与性能 |
| 量化 + Spec Decode | Draft/Target 格式、质量与接受率变化 | 接受长度、端到端加速、分布正确性 |
| Prefix Cache + DP | 缓存局部性被路由打散 | 命中率与实例热点 |
| Chunked Prefill + Spec Decode | 调度 token budget 竞争 | TTFT、TPOT、每轮接受长度 |
| Multi-LoRA + Prefix Cache | cache key 缺 Adapter 身份 | 跨 Adapter 污染与命中率 |
| P/D 解耦 + TP | KV rank/layout 映射 | 传输重分片、带宽和正确性 |
| CUDA Graph + 动态 shape | capture 范围、padding 与回退 | graph replay 率、显存、p99 |

## 4. 怎样判断组合有效

单项优化 A、B 与组合 AB 都在同一 workload 下测试。组合收益不要求等于两者相乘，但必须解释非线性：

$$
gain_{interaction}=gain_{AB}-gain_A-gain_B
$$

这里的 gain 应使用同一指标，例如成本/1M good tokens 或 SLO 内 goodput，而不是把显存节省与吞吐百分比相加。

## 5. 回退条件

为每项优化预先定义关闭开关、触发阈值与兼容配置。质量回归、p99 越界、错误率上升、显存不稳定或观测失真都应触发回退，而不是只看平均吞吐。
