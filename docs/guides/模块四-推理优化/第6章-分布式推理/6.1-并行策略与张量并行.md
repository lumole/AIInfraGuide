这一节解决两个问题：为什么单卡推理需要扩到多卡，以及张量并行究竟切了什么。阅读顺序是显存约束、四种切分方式、行列并行、通信成本，最后才是 vLLM 参数。

## 建议先读

**主教程**：[Harvard Kempner Institute：Large Language Model Distributed Inference Workshop](https://handbook.eng.kempnerinstitute.harvard.edu/_static/workshop/Kempner_LLM_Distributed_Inference_Workshop.pdf)。先读模型内存和 Tensor Parallelism 部分；它用连续的矩阵图解释切分与通信，并带练习，适合作为第一次学习的主线。

**补充图解**：[Hugging Face Ultra-Scale Playbook：Tensor Parallelism](https://huggingface.co/spaces/nanotron/ultrascale-playbook?section=tensor_parallelism)。这篇以训练为背景，但 row/column parallel 的图解清楚；只学习张量切分，不照搬训练性能结论。

读完应能自己回答：列并行何时需要汇集输出，行并行为何需要对部分和做归约，以及 TP 为什么优先放在高速互联域内。

## 1. 先判断为什么需要多卡

分布式推理常见目标有三个：让模型能够装入显存、降低单请求计算时间、提高服务总吞吐。这三个目标对应的方案并不相同。

| 策略 | 切分对象 | 一次请求经过几张卡 | 主要通信 | 主要目的 |
| --- | --- | ---: | --- | --- |
| TP | 单层矩阵、Attention head | 多张 | AllReduce / AllGather | 放下单层，缩短部分计算 |
| PP | Transformer 层 | 多张 | stage 间点到点激活 | 跨设备放下整个模型 |
| DP | 完整模型副本 | 一张或一组 | 入口请求路由 | 扩总吞吐与容错 |
| EP | MoE Experts | 多张 | token All-to-All | 放下并并行执行 Experts |

~~~mermaid

    W["先问瓶颈是什么"] --> M{"一份权重能否装入单卡?"}
    M -->|能| Q{"目标是更高总吞吐?"}
    Q -->|是| DP["优先 DP / 多副本"]
    Q -->|否| BASE["先保留单卡基线"]
    M -->|不能| L{"单层能否装入单卡?"}
    L -->|不能| TP["必须考虑 TP"]

    TOPO -->|是| PP["节点内 TP + 节点间 PP"]
    TOPO -->|否| MIX["比较 TP 与 TP x PP"]
~~~

## 2. 显存账本

模型权重只是显存的一部分。部署前至少估算：

$$
M_{total}=M_{weights}+M_{KV}+M_{activations}+M_{workspace}+M_{runtime}
$$

BF16 模型参数量为 $P$ 时，权重下限约为 $2P$ 字节。TP=$t$ 后单 rank 权重近似降为 $2P/t$，但 embedding、lm head、量化 scale、通信 buffer、CUDA Graph 内存池并不一定完全均分。KV Cache 又随并发、上下文长度和层数增长，因此不能只用“参数量乘位宽”决定 GPU 数。

## 3. 列并行

线性层 $Y=XW$ 的权重按输出维切成 $[W_1,W_2]$：

$$
Y=[XW_1,XW_2]
$$

每个 rank 持有同一输入 $X$，计算一部分输出通道。后续算子若可以继续消费分片结果，就保持分片；若需要完整 $Y$，再做 AllGather。通信点取决于相邻算子的切分方式，并非每个列并行层后都必须立即 gather。

## 4. 行并行

若按输入维切分 $X=[X_1,X_2]$、$W=[W_1;W_2]$：

$$
Y=X_1W_1+X_2W_2
$$

每个 rank 先算局部部分和，再用 AllReduce 得到完整输出。Megatron 风格实现交替安排列并行和行并行，尽量让中间张量保持分片，只在必要位置归约。

~~~mermaid
flowchart LR
    X["完整输入 X"] --> C0["GPU 0: XW0"]
    X --> C1["GPU 1: XW1"]
    C0 --> CAT["列并行输出<br/>拼接或继续分片"]
    C1 --> CAT
    CAT --> R0["GPU 0: X0W0"]
    CAT --> R1["GPU 1: X1W1"]
    R0 --> SUM["行并行输出<br/>AllReduce 求和"]
    R1 --> SUM
~~~

## 5. TP 为什么可能变慢

TP 减少每张卡的 GEMM 工作量，却在每个 Transformer block 引入 collective。Prefill 的矩阵较大，计算较容易掩盖通信；Decode 常是小 batch、小矩阵，通信延迟占比更高。量化缩短 GEMM 后，collective 比例还可能进一步上升。

判断 TP 是否有效，至少同时记录单请求 TPOT、固定并发吞吐、NCCL 时间占比和各 rank 利用率。“模型成功跑在四张卡上”只说明可运行，不说明扩展有效。

## 6. 推理特有的检查点

- Attention head 数和 KV head 数能否被 TP 整除；GQA/MQA 常是限制来源。
- logits、采样和词表并行在哪里汇合，是否产生额外通信。
- Prefix Cache 与 KV block 是否在各 rank 使用一致映射。
- 量化 checkpoint 的 group、scale 和 packed layout 是否支持当前 TP。
- GPU 间实际经过 NVLink、NVSwitch 还是 PCIe；不要只看设备数量。
