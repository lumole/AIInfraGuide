这节不是参数大全，而是一条实验路线。目标是证明多卡配置同时满足输出正确、模型与 KV 显存分布合理、性能相对基线确实提升。

## 建议先读

1. [Ray Serve：Deploy a vLLM Model](https://docs.ray.io/en/latest/serve/tutorials/vllm-example.html)：从配置、部署到请求的完整教程，适合第一次把 vLLM 放进 Ray Serve。
2. [Ray Serve：Cross-node Parallelism](https://docs.ray.io/en/latest/serve/llm/user-guides/cross-node-parallelism.html)：在前一篇基础上扩到多节点。
3. [Harvard Distributed Inference Workshop](https://handbook.eng.kempnerinstitute.harvard.edu/_static/workshop/Kempner_LLM_Distributed_Inference_Workshop.pdf)：回顾并行方式与性能判断。

教程能给出一条能跑的路径，但不能替代本站机器上的扩展实验。以下步骤把正确性、资源和性能验证串成完整流程。

## 1. 固定环境

| 类别 | 必须记录 |
| --- | --- |
| 模型 | 仓库、revision、dtype/量化格式、tokenizer、chat template |
| 软件 | vLLM、PyTorch、CUDA、driver、NCCL、Ray、镜像 digest |
| 硬件 | GPU、显存、节点数、GPU 拓扑、NIC 与网络 |
| 负载 | 输入/输出 token 分布、并发或请求率、采样参数、数据集版本 |
| 指标 | TTFT、TPOT/ITL、E2E、tokens/s、p50/p95/p99、峰值显存 |

没有完整环境记录的吞吐数字只能当现场观察，不能用于版本对比。

## 2. 建立最小基线

先用当前版本帮助确认参数，再启动能容纳模型的最小并行度。下面只是命令结构，不承诺字段在所有版本都相同：

~~~bash
vllm serve <model-id> \
  --tensor-parallel-size 2 \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.90
~~~

先发一个 greedy 请求验证输出，再逐步增加并发。第一次运行不要同时开启量化、Prefix Cache、Speculative Decoding 和自定义调度，否则出现变化时无法归因。

## 3. 做单变量扩展

按 TP=1、2、4 比较；若模型单卡装不下，就从可运行的最小 TP 开始。每档配置先预热，再用相同负载运行固定时长并重复多次。

若存在单卡基线，扩展效率可写为：

$$
E_n=\frac{\text{throughput}_n}{n\times\text{throughput}_1}
$$

$E_n$ 低不一定表示配置错误，但必须能由 collective、batch 形状或容量收益解释。单请求稍慢但 SLO 内总吞吐更高，也可能是合理结果。

## 4. 扩到多节点

跨节点前先完成 6.4 的拓扑检查，再用 Ray 或当前 vLLM 支持的 executor 启动。配置中明确节点数、每节点 GPU、TP/PP、placement、模型存储和服务端口。

~~~mermaid
flowchart LR
    B["单节点正确性基线"] --> T["单节点 TP scaling"]
    T --> N["网络与 NCCL 检查"]
    N --> R["Ray worker placement"]
    R --> M["跨节点模型加载"]
    M --> Q["固定负载压测"]
    Q --> C["与基线比较并归因"]
~~~

不要跳过单节点基线直接调跨节点问题，否则模型加载、显存、通信和编排错误会混在一起。

## 5. 三层验收

### 正确性

- 固定 seed 与 greedy 参数，比较不同并行配置的输出和停止位置。
- 检查 logprob 的允许数值误差，不要求浮点逐 bit 相同。
- 覆盖短输入、长输入、EOS、取消请求和超长拒绝。

### 资源

- 每个 rank 的权重、KV、workspace 和 CUDA Graph 池是否符合预期。
- 是否有一个 stage 或 rank 接近 OOM，而其他 GPU 大量空闲。
- 模型加载是否让共享存储或网络成为冷启动瓶颈。

### 性能

- 低并发看 TTFT/TPOT，高并发看 SLO 内 goodput。
- 同时报告 input/output tokens/s，避免只给 request/s。
- 用时间线确认 GEMM、collective 和 CPU 调度各占多少。

## 6. 故障记录模板

| 现象 | 第一批证据 | 常见方向 |
| --- | --- | --- |
| 所有 rank 卡住 | 各 rank 最后一条日志、NCCL 日志 | collective 顺序、rank/world size、网络 |
| 只有一个 rank OOM | 每 rank 显存和 stage 划分 | 非均匀模块、KV/graph pool、碎片 |
| 多卡反而变慢 | profiler 与 collective 时间 | 小 batch、PCIe/跨节点 TP、CPU 调度 |
| 输出不一致 | seed、采样参数、logprob、模型 revision | tokenizer、量化分片、数值误差 |
| 冷启动很慢 | 下载/读取带宽、各节点缓存 | 共享存储争用、重复下载、反序列化 |
