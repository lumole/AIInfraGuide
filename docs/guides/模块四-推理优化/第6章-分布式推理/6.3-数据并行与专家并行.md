DP 和 EP 都会出现多个计算单元，但工作粒度完全不同：DP 在请求入口选择一个完整副本；EP 则在每个 MoE 层按 token 把工作发给不同 Expert。

## 外部教程与资料缺口

[Hugging Face：Mixture of Experts Explained](https://huggingface.co/blog/moe) 用连续图解说明 Router、Expert、稀疏激活和负载均衡，适合先建立 MoE 直觉。[Harvard Distributed Inference Workshop](https://handbook.eng.kempnerinstitute.harvard.edu/_static/workshop/Kempner_LLM_Distributed_Inference_Workshop.pdf) 能补充请求副本和并行策略的位置。

现成入门教程通常把数据并行、Expert Parallel 和在线服务路由分开讲，缺少从一次请求到一次 token dispatch 的完整链路。下面依据 vLLM 的并行文档、Megatron-LM 和 MoE 论文补齐这段逻辑。

## 1. 数据并行：请求进入一个完整副本

~~~mermaid
flowchart LR
    R["请求入口"] --> L["负载均衡器"]
    L --> A["副本 A<br/>完整模型 + 独立 KV Cache"]
    L --> B["副本 B<br/>完整模型 + 独立 KV Cache"]
    L --> C["副本 C<br/>完整模型 + 独立 KV Cache"]
~~~

推理 DP 通常不做训练中的梯度同步。它的优势是故障边界清楚、横向扩吞吐直接；代价是每个副本都保存完整权重，而且 Prefix Cache、LoRA Adapter 和会话 KV 具有局部性。

入口路由不能只看请求数。长 prompt 与长输出的成本差异很大，更稳妥的负载估计应包含 waiting tokens、running tokens、KV 占用和预计完成时间。

## 2. 专家并行：每个 MoE 层都可能跨卡发送 token

MoE Router 为每个 token 选择 top-k Experts。若 Expert 分布在不同 rank，就要先 All-to-All dispatch，执行本地 Expert GEMM，再 All-to-All combine。

~~~mermaid
flowchart LR
    T["一批 token"] --> R["Router / top-k"]
    R --> D["All-to-All dispatch"]
    D --> E0["GPU 0: Experts 0,1"]
    D --> E1["GPU 1: Experts 2,3"]
    D --> E2["GPU 2: Experts 4,5"]
    E0 --> C["All-to-All combine"]
    E1 --> C
    E2 --> C
    C --> O["恢复 token 顺序"]
~~~

EP 的瓶颈经常不是矩阵乘，而是小消息、跨节点带宽和热点 Expert。平均 GPU 利用率看似正常时，单个 rank 仍可能因 token 倾斜成为尾延迟来源。

## 3. 两种路由发生在不同层级

DP 路由一次请求，决定它在哪个副本完成；EP 路由一层中的 token，而且下一层可能重新选择 Expert。DP 可保持会话粘性提高缓存命中，EP 则必须保证 dispatch/combine 后 token 顺序和权重一致。

| 维度 | DP | EP |
| --- | --- | --- |
| 路由对象 | 请求 | token |
| 路由频率 | 请求开始或重试时 | 每个 MoE 层 |
| 状态局部性 | KV、Prefix Cache、Adapter | Expert 权重与通信 buffer |
| 主要尾延迟来源 | 副本排队不均 | 热点 Expert、All-to-All |

## 4. 必须观测的指标

- DP：每副本 waiting/running tokens、Prefix Cache/Adapter 命中率、副本 p95/p99。
- EP：每 Expert token 数、dispatch/combine 时间、overflow/dropped tokens、每 rank 显存和执行时间。
- 组合部署：每个 rank 属于哪个 DP/TP/EP process group，以及高频通信是否跨节点。

假设 8 张 GPU，TP=2、DP=4 表示四个服务副本，每个副本内部用两卡 TP，不是八个独立模型。MoE 还可能在副本内使用 TP×EP；配置前应先把 process group 画出来。

## 5. 常见失败模式

1. **DP 扩容后缓存命中下降**：路由没有保留 prefix 或 Adapter 局部性。
2. **EP 平均吞吐正常、p99 很差**：少量请求产生热点 Expert 或跨节点 All-to-All。
3. **部分 rank OOM**：Expert 数量、通信 buffer 或 routed token 分布不均。
4. **扩 EP 后性能下降**：单 rank GEMM 太小，通信和 kernel launch 已超过计算收益。

## 自测

解释两个现象：增加 DP 后总吞吐上升但 Prefix Cache 命中下降；增加 EP 后权重能装下了但 p99 变差。答案应分别涉及请求局部性与 token 路由通信。
