流水线并行按层切模型。它减少高频跨节点集合通信，却让一个请求必须依次经过所有 stage，因此容量、吞吐和单请求延迟之间存在明确取舍。

## 建议先读

1. [Harvard Kempner Distributed Inference Workshop](https://handbook.eng.kempnerinstitute.harvard.edu/_static/workshop/Kempner_LLM_Distributed_Inference_Workshop.pdf)：主教程，先读 Pipeline Parallelism 部分。
2. [DeepSpeed Pipeline Parallelism Tutorial](https://www.deepspeed.ai/tutorials/pipeline/)：用 PipelineModule 示例和 3D 并行图把概念落到代码。
3. [Hugging Face Ultra-Scale Playbook：Pipeline Parallelism](https://huggingface.co/spaces/nanotron/ultrascale-playbook?section=pipeline_parallelism)：用时间线补充 bubble 和调度直觉。

这些材料大多以训练为背景。以下正文集中补齐在线推理差异：请求长度不同、Prefill/Decode 的形状不同，并且每个 stage 都维护本层 KV Cache。

## 1. 一个请求怎样穿过流水线

~~~mermaid
sequenceDiagram
    participant S0 as Stage 0 / layers 0..N
    participant S1 as Stage 1 / layers N+1..M
    participant S2 as Stage 2 / layers M+1..L
    S0->>S1: micro-batch A activations
    S0->>S1: micro-batch B activations
    S1->>S2: micro-batch A activations
    S1->>S2: micro-batch B activations
    Note over S0,S2: 首个 micro-batch 到达最后一级前，后级存在空闲
~~~

一个 stage 的时间若显著长于其他 stage，整条流水线吞吐由它决定。简单按层数平均切分通常不够，因为 embedding、Attention、MLP、MoE 和 lm head 的成本并不相同。

## 2. 推理中的三类气泡

1. **填充与排空**：首个 micro-batch 尚未到达后级，或最后一个已经离开前级。
2. **stage 不均衡**：慢 stage 让其他 GPU 等待。
3. **请求形状抖动**：不同 prompt/output 长度使各 stage 的实际时间不断变化。

增加 micro-batch 可以摊薄第一类气泡，但也会增加排队时间和显存占用。在线服务不能只追求设备利用率，还要同时约束 TTFT 和 p99。

## 3. TP 与 PP 为什么经常组合

TP 几乎每个 Transformer block 都有 collective，适合放在 NVLink/NVSwitch 域内；PP 只在 stage 边界发送激活，跨节点频率较低。因此常用“节点内 TP、节点间 PP”：

~~~mermaid
flowchart LR
    subgraph N0["节点 0 / PP stage 0"]
      G0["GPU 0 / TP 0"] <--> G1["GPU 1 / TP 1"]
    end
    subgraph N1["节点 1 / PP stage 1"]
      G2["GPU 2 / TP 0"] <--> G3["GPU 3 / TP 1"]
    end
    IN["tokens"] --> G0
    G1 -->|"stage activations"| G2
    G3 --> OUT["logits"]
~~~

## 4. 划分 stage 的步骤

1. 测量单层 Attention、MLP、MoE 和非重复模块的 Prefill/Decode 时间。
2. 估算各 stage 的权重、KV 和 workspace 峰值，而非只统计层数。
3. 让高频 TP collective 留在节点内，stage 边界再跨节点。
4. 分别用长 prompt/短输出和短 prompt/长输出验证平衡。
5. 记录每个 stage 的执行、传输、空闲时间和最大显存。

## 5. 什么时候不该用 PP

模型单卡可装下、并发很低且 TTFT 极敏感时，PP 的传输和填充开销可能没有收益。若只为扩大总吞吐，多个完整副本通常更直接。PP 的主要价值是跨设备放下模型，并在足够多 micro-batch 时取得可接受吞吐。
