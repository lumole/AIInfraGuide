多节点部署最容易犯的错，是先写启动命令，后看物理拓扑。本节从 GPU 间数据路径开始，再解释 Ray、vLLM、NCCL 和网络分别负责什么。

## 外部教程与资料缺口

[Ray Serve：Cross-node Parallelism](https://docs.ray.io/en/latest/serve/llm/user-guides/cross-node-parallelism.html) 围绕 LLM 服务给出多节点配置与示例，适合跟着完成一次部署。[Hugging Face Ultra-Scale Playbook：Network Anatomy](https://huggingface.co/spaces/nanotron/ultrascale-playbook?section=network_anatomy_of_a_multi-node_training_setup) 用图展示节点内外互联层次，可先用来建立硬件路径概念。

前者偏操作，后者偏硬件，而且都没有完整解释“物理拓扑如何变成 vLLM rank 与 process group”。下面依据 Ray、vLLM 与 NCCL 一手资料补齐这一段。

## 1. 四层职责

| 层 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Ray / 编排器 | 进程启动、资源声明、placement、故障重建 | GPU collective 的实现细节 |
| vLLM executor | 划分 rank、模型加载、请求调度 | 选择物理交换机路径 |
| NCCL | AllReduce、AllGather、All-to-All、P2P | 决定业务请求去哪个副本 |
| 网络与驱动 | PCIe/NVLink/RDMA 数据传输 | 修正错误的 rank 拓扑 |

~~~mermaid
flowchart TB
    API["服务请求"] --> RAY["Ray / 编排<br/>放置 worker"]
    RAY --> V["vLLM executor<br/>建立 TP/PP/EP groups"]
    V --> NCCL["NCCL collectives"]
    NCCL --> NV["节点内 NVLink / PCIe"]
    NCCL --> RDMA["节点间 InfiniBand / RoCE / TCP"]
~~~

Ray 能把 worker 放到某张 GPU 上，但不会自动保证高频 TP group 都落在 NVLink 域内。NCCL 能为 collective 选择路径，但无法弥补一开始就错误的分组。

## 2. 先画物理拓扑

部署记录至少包含：

- 每个节点的 GPU 型号、数量及 GPU 到 CPU NUMA 的关系；
- GPU 间 P2P、NVLink 或 NVSwitch 连接；
- NIC 所属 NUMA、标称与实测带宽、MTU、RDMA 能力；
- 容器内实际可见的 GPU、网卡和共享内存；
- 模型文件来自本地盘、对象存储还是共享文件系统。

原则是让高频通信组留在最快链路内：TP 通常放节点内；PP 可跨节点；EP 是否跨节点取决于 All-to-All 和网络能力。仅按 GPU 编号连续分组不一定得到正确映射。

## 3. 从物理设备到 rank

先为每个进程写一行表格：节点、GPU、global rank、local rank、TP group、PP stage、EP group。然后检查每个 group 的成员是否符合预期。

例如两节点各四卡、TP=4、PP=2 时，节点 0 的四个 rank 构成 stage 0 的 TP group，节点 1 的四个 rank 构成 stage 1 的 TP group；跨节点只在 stage 边界发送激活。若把 TP rank 交错分布在两个节点，高频 collective 就会跨网卡。

## 4. 多节点启动前的五道门

1. **环境一致**：镜像、驱动兼容性、CUDA、vLLM、PyTorch、NCCL、Ray 和模型 revision 一致。
2. **连通性正常**：worker 能解析彼此地址，端口、路由、防火墙和时钟同步已确认。
3. **模型数据可用**：每节点本地缓存或共享存储策略明确，冷启动峰值带宽可承受。
4. **通信路径正确**：NCCL 选中的 NIC、P2P 和 RDMA 与拓扑设计一致。
5. **进程放置可核对**：每个 rank 的节点、GPU 和 process group 都能从日志还原。

## 5. 故障定位顺序

~~~mermaid
flowchart TD
    F["启动卡住或吞吐异常"] --> P{"单节点基线正常?"}
    P -->|否| LOCAL["先查模型、显存与单机通信"]
    P -->|是| NET{"节点间基础带宽和连通正常?"}
    NET -->|否| FABRIC["查 NIC、MTU、RDMA、路由"]
    NET -->|是| MAP{"rank 与 GPU/NIC 映射正确?"}
    MAP -->|否| PLACE["修正 placement 与 process groups"]
    MAP -->|是| TRACE["收集 NCCL 日志和时间线"]
~~~

不要一开始就增大 timeout。超时通常只是症状，真正原因可能是 world size 不一致、一个 worker 已经 OOM、网卡选择错误、共享内存不足或 collective 顺序不一致。

## 6. 应保存的证据

一次多节点实验应保存 Ray 资源视图、rank 映射表、GPU 拓扑、NCCL 选路日志、启动配置、各节点时间同步状态和压测结果。只有这些证据齐全，才能区分模型问题、调度问题与网络问题。
